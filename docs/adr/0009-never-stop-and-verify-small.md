# ADR-0009：run を止めずに直し、開発は最小規模の実機で確かめる

- 状態：Accepted
- 日付：2026-10-12

## 背景
Phase 1 の実機の確認（gpt-oss:20b、短編、約1,260タスク）で、run が何度も止まり、確認に数日かかった。
- タスクが1つ試行の上限まで不合格になると、run 全体が `stalled` になり、人が直すまで進まなかった（固有名詞の誤検出、字数の超過、選択肢の書き方の揺れ）。
- 欠陥を見つける手段が、分量の最低ライン（ADR-0007）を満たす実機の run だけだった。1回の確認に半日から丸一日かかり、欠陥を1つ直すたびに一晩待った。テストは LLM の応答を偽物で置き換えるため、本物のモデルの振る舞いは実機で回すまで見えなかった。
- 中心の流れ（推論・検証・再試行）が本物のモデルで安定する前に、表や配分などの広がりを先に作った。

所有者は、不合格なら自分で直して完了まで進むべきこと、字数の超過なら短くする推論をすればよいこと、人間に見張りを強いる計画は誤りであることを指摘した。

## 判断
1. **run を止めない**。タスクが不合格になったとき、次の順に扱う（[task-model.md](../spec/task-model.md) §6.7）。
   1. 修正の推論：不合格の理由が出力の手直しで解消できるもの（字数の超過・不足、文末の欠け、書き方の揺れ）は、元の出力と理由を入力に、手直しする推論を1回行う（例：上限を超えた文を上限内に短くする）。
   2. 実行者の格上げ：試行の上限に達したら、設定した上位の実行者で、同じカードをもう一度推論する。
   3. 記録して進む：それでも合格しなければ、そのタスクを `skipped` にし、失敗の報告（`failure.md`）と manifest の `warnings` に残して、run を進める。後続のタスクは、その要素を「未定」として扱う。
   run が止まるのは、ハーネスの変更（`halted`）と、実行環境の問題（通信の失敗が続く等）だけとする。
2. **開発の確かめ方**。すべての種類の LLM タスクを本物のモデルで1回以上通す、開発用の最小規模（`dev`）を設ける。`dev` の run は数分で終わる大きさとし、作業項目ごとの受け入れ条件に「`dev` の実機の run が止まらずに通る」を含める。分量の最低ラインを満たす run は、各フェーズの完了時に1回だけ行う。`dev` は開発の確認用で、ユーザー向けの規模プリセットではない（分量の最低ラインは変えない）。
3. **人間に見張りを求めない**。開発と確認の run は、所有者の端末が眠っていても進む環境で回す。所有者の役割は、原則の判断と、フェーズ完了時の結果の確認とする。

## 理由
- 無人で完走させることは VISION の P7 そのものであり、1つの要素の失敗で全体を止める作りはこれに反する。失敗の記録は残るので、欠陥は後から直せる。
- 欠陥の多くは本物のモデルでしか現れない。数分で回る確認を変更のたびに行えば、欠陥を一晩ではなく数分で見つけられる。

## 影響
- task-model §6.3 の「1つの要素が試行の上限まで不合格になるのはハーネスの欠陥とみなし `fail` とする」を改め、§6.7 の扱いに置き換える。`on_exhausted` の既定は `skip` とする。
- 計画：Phase 1 に P1-37（止めない失敗の扱い）と P1-38（`dev` 規模と実機の確認）を加え、Phase 1 の残りと Phase 2 以降の作業項目の受け入れ条件に `dev` の実機の run を含める。
