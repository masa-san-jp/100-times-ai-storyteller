# VISION：目的と設計原則

- 所有範囲：目的、設計原則 P1〜P8

## 1. 目的

100 TIMES AI シリーズ（[LINEAGE.md](LINEAGE.md)）の系譜として、**外部のAIエージェントが参照して実行するだけで、物語が自律的に生成・出力されるエージェントハーネス**を作る。

- リポジトリの中にAIはいない。コーディングエージェント、ローカルLLM、クラウドのチャットモデルが、このリポジトリの手順に従ってタスクを実行する。
- 出力は2段で作る。
  1. **物語生成ハーネス**：「いつ・どこで・誰が・何のために・何をして・どうなった」を記述した説明的な**正本**を作る。
  2. **様式化ハーネス**：正本を、ユーザーが選んだ様式（小説・映画シナリオ・プレゼンテーション等）に整形する。
- 人間がいない間に、実行者の数だけ物語が並行して出力される。1本あたりの速度より、止まらないこと・再開できること・並行できることを優先する。

## 2. なぜこの設計なのか

LLMの内部知識は、ユーザーのものではない。予め意図が含まれた推論であり、全体を任せると出力は中庸に収斂する。
物語の各要素は、分解された工程の中で、ユーザーの入力と要素テーブルから生成されなければならない。
LLMはハーネスに従って実行する役目であり、作者ではない。

## 3. 設計原則

以下の原則は、すべての spec・実装・タスク定義に優先する。原則に反する変更には ADR が必要である。

### P1. LLMは部品であり、作者ではない
- LLMが受け取るのは、1つのタスクカードだけである。タスクカードには、固定された入力・処理手順・出力スキーマだけを含む。
- LLMに全体像を見せない。パイプライン全体、他のタスク、最終的な物語の姿を、タスクカードに含めない。
- LLMは求められた出力だけを推論する。前後のタスクを先回りしたり、全体を要約・統合したりさせない。

### P2. 確定できる処理はコードで行う
選択・ランダム割当・組み合わせ・抽出・検索・構造の展開・派生値の計算・検証・重複除外・組み立ては、決定的なコードで行う。LLMには行わせない。

### P3. 素材の出所を限定し、追跡できるようにする
- 物語の素材は、(1) ユーザーの入力、(2) 要素テーブル、(3) 前段タスクの出力、の3つからのみ供給する。
- LLMタスクの出力には、使った素材のID（`sources`）を付けさせ、コードがその実在を検証する。

### P4. 中庸への収斂を構造で防ぐ
- 要素の組み合わせは、コードが seeded random で決める。
- LLMに「最も良いもの」を選ばせない。候補を複数生成させ、コードが選ぶ。
- 要素テーブルは、生成のたびに対極の要素を加えて自己増殖させる。
- 生成物どうしの重複・近似重複を、コードで検出して除外する。

### P5. 小さいローカルモデルで完走できる
- 1タスクの入力は、コードが管理する文字数予算に収める。出力は1項目、または小さなJSONに限る。
- 検証に失敗したタスクは、エラー内容を添えて再実行する。
- 目標とする最小の実行者は、一般的な個人用マシンで動くローカルモデル（20B前後）である。

### P6. すべての中間出力を保存し、再利用する
- タスクの入出力をすべて保存し、どこからでも再開できるようにする。
- 同じ入力のタスクは再実行せず、保存済みの出力を再利用する。

### P7. 並列・無人で進む
- 物語1本 = run 1つ。run どうしは独立している。
- タスクは claim してから実行する。何体の実行者がいても、同じタスクを二重に実行しない。

### P8. ナラティブは傾向だけを持ち、個人情報を含めない
- ナラティブに書くのは、ユーザーがどのような傾向を持っているかだけである。個人を特定できる情報は書かない。
- 個人情報の検出はコードで行い、該当があれば取り込みを拒否する。
- ナラティブ・入力・生成物はユーザーのローカルディレクトリにだけ置き、リポジトリに含めない。コードはネットワーク通信を行わない（localhost のローカルLLMアダプタを除く）。
