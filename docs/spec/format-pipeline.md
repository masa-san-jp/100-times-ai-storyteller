# spec: 様式化ハーネス

- 所有範囲：F0〜F4 の各段階、様式プロファイルの形式、提供する様式と、その単位の決め方

## 1. 全体の流れ

```
正本 → F0 様式選択[C] → F1 分割[C] → F2 単位ごとの整形[L] → F4 検証[C+L] → F3 組み立て[C]
```

- 様式化は、正本1つに対して、様式ごとに独立して実行する。同じ正本から複数の様式を並行して作れる。
- 様式化は、正本の run の中に `formats/<name>/` として作る。タスクは同じ DAG に追加する。
- 正本は変更しない。

## 2. 様式プロファイル

`formats/<name>/profile.yaml` に置く。形式は `schemas/format-profile.schema.json` で検証する。

```yaml
name: novel
unit: chapter                    # 単位：chapter | scene | slide | section
unit_mapping: structure          # 単位への割付方法（§4）
chars_per_event: [1500, 3000]    # 出来事1件あたりの分量（下限・上限）
max_chars_per_task: 6000         # F2 の1タスクで書かせる分量の上限
template: template.md            # F3 で使うテンプレート
continuation: true               # F2 タスク定義の continuation に渡す（task-model.md §8）

rules:                           # F2 のタスクカードに入れる規則
  - 地の文と会話で書く。説明的な要約で済ませない。
  - 入力の出来事の順序を変えない。
  - 入力にない出来事・人物を加えない。

checks:
  code: [min_chars, max_chars, ends_complete]   # 字数の範囲は、単位の出来事数 × chars_per_event から F1 が計算して各タスクに渡す
  llm:
    - 入力の出来事のうち、描かれていないものがありますか
    - 入力にない人物が登場していますか
```

## 3. 各段階

### F0 様式選択 [C]
- 様式プロファイルを読み込み、正本の出来事数から全体の分量の範囲を計算する。

### F1 分割 [C]
- 正本の events を、`unit_mapping` に従って単位に割り付ける（§4）。
- 1単位の分量の上限が `max_chars_per_task` を超える場合、その単位を、出来事の区切りで複数の F2 タスクに分ける。
- F1.split v4 以降は、出来事を語る様式（unit_mapping が出来事を割り付ける novel・screenplay・slides）の各部分に、部分の `characters` と同じ人物・同じ順で、正本 `cast` の `motive` を `motives`（`[{"name": 名前, "motive": 原文}]`）として写す。値を要約・言い換えしない。`motive` が `（未定）` と完全に一致する人物は含めない。該当者がいなければ空の配列とする。資料集・画像プロンプトなど、出来事を語らない様式の部分には `motives` のキーを置かない。旧版の F1 出力には `motives` がなく、従来どおり扱う。

### F2 単位ごとの整形 [L]
- タスクの単位：F1 が作った単位（または分割した部分）1つ。
- 入力：その単位の events、登場する人物の名前・読み・役・プロフィール、様式の規則、分量の範囲、直前の単位の末尾（コードが 600字を切り出す）。正本の他の部分は渡さない。
- F2.write・F2.write_once v3 以降は、入力スロット `motives`（label「登場人物の動機」、`from: F1.split`、`select: parts[{slot}].motives`、`required: false`、`truncate: none`）を `characters` の直後に加える。カードの steps は変えない。動機は切り詰めない。予算が足りない場合は task-model §3.2 の順（`previous_unit` → `characters` の順に縮み、`motives`・`conditions` は縮まない）に従い、それでも収まらなければ §3.2 の入力生成の失敗とする（S5 の motive は120字以内で、通常は起きない）。`motives` がない、または空の配列の場合は、スロットを表示しない。
- 動機の表し方は様式の規則に置く。novel・screenplay・slides の profile の `rules` に「登場人物の動機は、その人物の行動・台詞・内面で示す。動機を示すために、入力にない出来事を加えない。」を加える（slides は「行動・台詞」を「行動・発言」と読み替えず、同じ文を置く）。
- 出力：本文（`output: text`）。
- F1.split v2以降が作る同一様式の2つ目以降のF2は、直前のF2本文に加え、そのF4.verifyの完了にも依存する。直前本文が不合格で無効化・再生成されている間は、後続のF2をclaimしない。これにより未確定本文を入力にした後続生成の巻き添えを防ぐ。様式間の並列性、同一部分の各質問の並列性、入力素材/字数/試行/無効化/省略/警告付き採用の既存契約は変更しない。最初のF2とF3の組立条件は従来どおり。F1 v1は従来の依存グラフを保持し、版を変えただけで既存done済みF1を自動再展開しない。

### F4 検証 [C+L]

#### 対象を限定した検査（P3-09）

F1.split v3以降と、構造化した`checks.llm`を持つプロファイルは、以下の検査を使う。従来の質問文字列配列、旧F1出力、F4.judge v2は従来の処理を維持する。新版の仕組みを旧done済みF1へ自動で適用しない。

- `checks.llm`は、従来の文字列配列、または`kind`・`question`・`severity`を必須とするオブジェクトの配列を受け付ける。混在は拒否する。kindは`event_coverage`・`named_actor`・`condition_conflict`・`replay`、severityは`error`・`advisory`。`replay`はadvisoryだけを許す。小説・脚本・スライドはこの構造化指定へ移行し、最初の3種類をerror、replayをadvisoryとする。値と質問文の原本は各profileとする。
- F1は各部分の`reviews`に対象をCODEで展開し、`kind`・`question`・`severity`・`source`を保存する。event_coverageは対象出来事1件ごとに`source={id,what,result}`、named_actorは部分1つにつき`source={characters:[{name,reading}]}`、condition_conflictは対象部分の重複を除いた確定条件1件ごとに`source={condition}`、replayは部分1つにつき`source={}`とする。条件がなければcondition_conflictの推論は作らない。並びはprofile順、出来事/条件の元の順とする。資料全体、人物プロフィール、別の出来事の項目を補助文脈として足さない。
- 各対象について新しい`F4.review`のLLMタスクを1件作る。これは1つの対象について1つの質問だけを判定する。既存のF4.judgeとキャッシュを共有しない。F4.verifyはこの部分の全reviewを待ち、後続F2は従来どおり前verify完了を待つ。様式間・同一部分のレビュー間は並列でよい。
- 入力は1件のreview、対象部分の本文、様式名とする。上限14000字を維持し、source/本文は切り捨てない。スライドはCODEで画面表示とノートの語りを区別した検査表示を作る。HTMLコメントの区切り以外の文字・順序を保持し、不正構文では元本文を使う。引用の照合対象はラベルを含まない元本文とする。元F2/F3出力は変更しない。
- event_coverageは、指定されたwhat/resultの行動・結果の欠落だけを調べる。人物一覧から各人の必須行動を補わず、時刻/場所/感情や入力にない具体語句の非再掲を欠落としない。言い換え・台詞・スライドの語りも描写として読む。明確に欠落と判断できなければunknownとする。
- named_actorは、許可名/読み以外の明示的に名付けられた人物を、新たな行動・台詞の主体として追加しているかを調べる。匿名の背景集団、単なる名前への言及、別名か判断できないものを勝手に違反と断定しない。
- condition_conflictは、渡した条件1件の前提・禁止・帰結を、本文の明示的な行動/結果が覆しているかだけを調べる。描かれていない条件の発動を補わず、能力の説明だけを新しい筋の条件としない。追加条件が元の成立条件を否定する場合も対象。本文と条件の意味を比較できなければunknownとする。
- replayは進展のない行動/結果の再演に関する助言であり、自動無効化に使わない。意図した要約、回想、画面と語りの重なりを機械的な不合格条件にしない。
- 出力は`answer: yes|no|unknown`、`reason`、`source_quote`、`body_quote`、`subject`の5フィールド。reason以外の引用/subjectは該当なしなら空文字。yesのevent_coverageではsource_quoteが対象what/resultのいずれかの全文と一致する必要がある。その全文が本文に実在するなら、不整合な判定としてunknown扱いにする。yesのcondition_conflictではsource_quoteが対象条件の全文と一致し、空でないbody_quoteが元本文の部分文字列である必要がある。yesのnamed_actorでは空でないsubjectがbody_quote内に実在し、body_quoteが元本文に実在し、subjectが許可名/読みのNFKC正規化後の完全一致ではないことを必要とする。CODEは引用の実在と対象の一致を検査するが、意味の正しさまで証明するとは扱わない。
- 不足/不正な引用、unknown、reviewの省略は未確認として記録し、本文は保持する。意味判定の引用不備を直すためにモデルを自動再呼出ししない。noも、示された引用が原文に存在しない場合は未確認とする。schemaの型/必須項目の検査は通常の提出契約に従う。
- F4.verifyは`assessment: passed|failed|unresolved`を出力する。CODE検査不合格またはerrorのyesで上記引用条件が揃ったときだけfailedとして従来の無効化上限へ進む。優先順位はfailed、unresolved、passedの順とし、failedの条件が1件でもあれば他の未確認によって上書きしない。failedの条件がなく未確認があればunresolved、いずれもなければpassedとする。`passed`の真偽値はassessmentがpassedのときだけtrue。advisoryのyesは助言としてwarningsに残す。unresolvedはwarningsに検査対象と理由を残し、自動無効化しない。ファイル出力/全体のcompletedと、未確認なしの検査通過を混同しない。既存のCODE検査・字数・skip・無効化上限・品質上限時の採用方針を変えない。

#### 旧形式の検査

- [C] `checks.code` の検査と、書式の構文（Fountain、Marp）。
- [L] `checks.llm` の質問を1つずつ、別のタスクとして yes/no で問う。入力は、その単位の events と本文だけ。期待する答えはすべて `no` とする。
- 不合格の単位の F2 タスクを無効化する（[task-model.md](task-model.md) §4.3）。F2 の `max_invalidations` は2とし、超えた場合は F2 の `on_exhausted`（既定は `skip`）に従う。`skip` の単位は本文を F3 で「（未定）」として示し、run は止めない（§6.7）。

### F3 組み立て [C]
- テンプレートに単位の本文を流し込み、最終ファイルを `formats/<name>/` に出力する。
- 省略された単位（F2 が `skipped`）は、本文を「（未定）」とし、manifest の `warnings` に記録する。
- テンプレートは、`{{#units}}…{{/units}}` の1ブロックを単位ごとに繰り返す。ブロックの中では `{{unit.number}}`（通し番号）、`{{unit.chapter}}`（部がある場合は部ごとに数え直した番号。部がなければ `{{unit.number}}` と同じ）、`{{unit.id}}`、`{{unit.title}}`、`{{unit.part}}`、`{{unit.body}}` を使える。`{{#part_start}}…{{/part_start}}` で囲んだ部分は、各部の最初の単位にだけ出力する（大河の部の見出し用。部がない場合は出力しない）。
- 書式の構文検査は、`checks.code` に名前で加える。`fountain_syntax` は、映画シナリオ（`screenplay`）の F2 の本文（シーンの中身）を検査する。本文にはシーン見出し（行頭の `.`）・節（`#`）・要約（`=`）を書けない（見出しはテンプレートが付ける）。台詞は、強制の人物名（行頭の `@`）の行と、その直下の台詞の行で構成する。人物名の前は空行とし、人物名の直後に台詞の行が必要である。括弧書き（半角の丸括弧で囲んだ行）は台詞の中にだけ書ける。ノート（`[[ ]]`）とボーンヤード（`/* */`）は閉じていなければならない。組み立てた全体（タイトルページ、シーン見出し1つ以上）の検査関数もあるが、F4 の検査対象は F2 の本文である。

## 4. 提供する様式

| 様式 | `name` | 単位 | `unit_mapping` | 出力形式 | 導入 |
|---|---|---|---|---|---|
| 小説 | `novel` | 章 | `structure` | Markdown | P3-02 |
| 映画シナリオ | `screenplay` | シーン | `scene` | Fountain | P3-03 |
| プレゼンテーション | `slides` | スライド | `per_event` | Marp Markdown | P3-04 |
| 画像プロンプト | `visual-prompts` | 人物・場面（`prompt`） | `person_and_event`（§4.3） | Markdown | P5-01 |
| 資料集 | `reference-book` | 世界セクション・人物 | `world_cast` | Markdown | P5-02 |

### 4.1 `unit_mapping` の定義

| 値 | 割付 |
|---|---|
| `structure` | 主筋の構造テンプレートの段階を章にする。副筋のスロットは、時系列でその直前にある主筋のスロットと同じ章に入れる（最初の主筋のスロットより前にある場合は第1章に入れる）。大河では部ごとに章を数え直し、部の見出しをテンプレートで加える。`tables/structures.yaml` に章への割付がある場合はそれに従う（heros-journey-12 には、heros-journey の12段階→10章の割付を P3-02 で加える） |
| `scene` | 連続する出来事のうち、`where` が同じで、`when` が連続しているものを1シーンにまとめる。`where` が変わる、または `when` が「翌日」「数年後」など時間の飛躍を示す場合に、新しいシーンにする。時間の飛躍の判定は、`tables/time_jumps.yaml` の語句（`phrases`）が `when` に含まれるかどうかで行う（P3-03）。出来事は正本の events の並びのまま割り付ける。シーンの見出しは、シーンの最初の出来事の「`where` - `when`」とする |
| `per_event` | 出来事1件を1単位にする |
| `world_cast` | 出来事ではなく、世界の概説・世界セクション・人物を1単位にする（§4.4） |

### 4.2 プレゼンテーション様式の目的

`slides` は、**物語そのものをスライドで語る**様式である（物語の紹介資料ではない）。

- 出来事1件を1枚のスライドにする。各スライドは、見出し（出来事を表す1行）、本文（3行以内）、スピーカーノート（語りの原稿、`chars_per_event` の範囲）を持つ。
- 最初に表紙（題名）、最後に結びのスライドを、テンプレートで加える。題名は、正本の主人公の名前とプロット型から、テンプレートで作る（LLM に作らせない）。
- F2 の出力は1枚分の Markdown とする：1行目が `# ` で始まる見出し、続く 1〜3 行の本文、最後に `<!-- … -->` で囲んだスピーカーノート。スライドの区切り（`---`）と front matter は書かせない（テンプレートが加える）。
- F4 の `checks.code` に `marp_syntax` を加える。上の形（見出し1つ、本文 1〜3 行、空でないスピーカーノート1つ、区切りなし）を満たすか検査する。
- スライドの枚数は、出来事数 + 2（表紙と結び）とする。F3 は、テンプレート（`formats/slides/template.md`）で front matter（`marp: true`）、表紙、各スライド、結びを `---` で区切って組み立てる。出力は `formats/slides/slides.md`。

### 4.3 画像プロンプト様式 `visual-prompts`

`visual-prompts` は、画像生成AIに渡す**人物の全身像**と**場面の絵**のプロンプトを作る様式である（heroes の全身画像の系譜）。物語の本文は作らない。

- 単位は `prompt` とし、`unit_mapping: person_and_event` で割り付ける。正本の cast の人物1人を1単位、events の出来事1件を1単位とする。単位は、人物（cast の並び順）、出来事（events の並び順）の順に並べる。単位数は、人物数 + 出来事数に等しい。
- 人物の単位：入力は、その人物の名前・読み・役・プロフィール・外見、およびその人物が `who` に含まれる出来事のうち先頭の3件（参照用。この単位の対象ではない）。出力は、全身像のプロンプト1つ（外見・服装・体格・表情・姿勢）。
- 場面の単位：入力は、その出来事1件と、`who` の人物の名前・読み・役・プロフィール・外見。出力は、場面のプロンプト1つ（構図・場所・時間帯・光・人物の位置と動き・感情）。
- 出来事は、`unit_mapping` の割付では必ず1回ずつ割り付ける。人物の単位は出来事を割り付けない（上の参照用の出来事は、割付の対象としない）。
- 分量は、プロンプト1つあたり `chars_per_event` の範囲とする（人物の単位も同じ範囲を使う）。`continuation` は `false` とする。
- 規則：プロンプトは日本語の文で書く。人物は名前ではなく外見で描写する。入力にない人物・外見・場所を加えない。画像に文字や台詞を入れる指示を書かない。実在の人物・作品・商標の名前を使わない。
- 単位の見出しは、人物は「人物：名前」、場面は「場面：出来事の段階名」とする。出力は、これらの見出しを付けて1つの Markdown にまとめる。

### 4.4 資料集様式 `reference-book`

`reference-book` は、正本の**世界設定と人物を資料としてまとめる**様式である（物語の本文は含めない）。単位は出来事ではなく、世界セクションと人物とする。プロファイルは `unit: section`、`unit_mapping: world_cast` とする。

- 単位は、次の順にコードが作る。
  1. 世界の概説：`world` の `place`・`era`・`object`、`theme` がある場合は `theme`。
  2. 世界セクション：`world.sections` の1つにつき1単位（セクションの `body` と `items`）。
  3. 人物：`cast` の1人につき1単位（名前・読み・役、紹介・プロフィール・動機・外見・性格・価値観・話し方・内面の葛藤、過去、関係、口癖）。
- 世界セクションと人物は、1つも欠けずに、ちょうど1単位に入れる。
- 単位の中の資料項目（セクションの `body`、`items` の1件、人物の1つの欄）を、F2 に渡す「出来事」の入力として扱う。`chars_per_event` は資料項目1件あたりの分量とする。1単位の分量が `max_chars_per_task` を超える場合は、資料項目の区切りで複数の F2 タスクに分ける。
- F2 の入力は、その単位の資料項目だけとする。他の単位と、物語の出来事は渡さない。
- F4 の `checks.code` に `contains_names` を加える。`items` の名前と人物の名前が、その F2 の本文にあることを検査する。
- F3 は、概説・世界セクション・人物の順に、単位の見出し（`世界：…`、`人物：…`）を付けて組み立てる。

### 4.5 筋の条件と本文の品質
- F1 は重複した出来事を除外してから割り付け、各部分に関係する筋の確定条件を保持する。F2 と F4 のカードにも渡す。F2 は入力にない発動・禁止・解決の条件を加えない。
- 出来事を語る様式では、F4 に条件の追加・矛盾と同じ行動・結果の再演を問う判定を各1件追加する。構造の説明と内部 ID は F2 の提出時と F4 のコード検査で不合格にする。提出時の不合格は元の本文と理由を渡す修正の推論で直す。
- 様式プロファイルの最上位キー `submit_checks`（任意）は、F2 の提出時にも行うコード検査の一覧である。書き方は task-model §6.2 の `validate.checks` と同じ（検査名の文字列、または検査名→引数の1キーの対応表）の配列とし、format-profile スキーマに加える。使えるのは text に適用でき、カードの入力に依存しない検査だけ（初期は `no_repeated_sentence` のみ許可し、他の名前はスキーマで拒否する）。F4 のコード検査（`checks.code`）には加えない。
- F1.split v5 以降は、出力の最上位に `submit_checks` を写す（指定がなければ空の配列）。F2.write・F2.write_once v4 以降は、提出時の検証（キャッシュ一致時の検証を含む）で、タスク定義の `validate.checks` の後にこの一覧を加えて検証する。通常のカードには示さない。修正カードの「満たすべき条件」には、既存の各検査の条件文で示す。
- 小説（novel）は `submit_checks: [{no_repeated_sentence: {exclude_quoted: true, excerpt: true}}]` を指定し、地の文の同じ長い文の反復を提出時に拒否する。台詞のリフレインやノートの言い換えを誤検出するため、脚本・スライドには指定しない。F4 の replay（advisory）は変えない。
- 継続（task-model §8）で連結した F2 本文が提出時の検証で不合格になった場合、F2.write v4 以降は、修正の対象かどうかによらず `partial.md` を破棄し、`continuation_step` を0に戻す。その試行の記録（`attempts/<n>.json`）の `output` は、最後の断片ではなく連結した全体とする。次のカードは、修正の対象なら修正カード（元の出力は連結した全体。6000字を超える場合は既存の中間省略に従う）、そうでなければ通常のカードとする。修正の提出が途中で切れた場合は、§8 の通常の継続として扱う。
- この節の品質判定だけが不合格で F2 の無効化上限に達した場合は、未解決の理由を warnings に記録し、最後の本文を採用して進む（ADR-0009）。
