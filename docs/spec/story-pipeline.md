# spec: 物語生成ハーネス

- 所有範囲：S0〜S9 の各段階の入力・処理・出力、素材と要素のID、要素の軸とプール、プロット型と構造テンプレート、名前の生成、正本の構成、重複除外とバッチの補充

`[C]` はコードタスク、`[L]` はLLMタスクを表す。`[C+L]` の段階は、LLMタスクとそれを受けるコードタスクの2種類のタスクで構成する。
すべての LLM タスクの出力は、空でない `sources` を持ち、`sources_exist` で検証する（P3）。タスク定義の形式は [task-model.md](task-model.md) による。
この文書に書いた各タスクの数値（候補数・字数・件数・共有の有無）は初期値である。タスク定義（`harness/story/tasks/*.yaml`）を作成した時点で、そのタスク定義が原本になり、この文書の数値はタスク定義へのリンクに置き換える（[docs/README.md](../README.md) §2.1）。

## 1. 全体の流れ

```
S0 入力取り込み[C] → S1 素材抽出[L] → S2 要素プール拡張[L] → S3 組み合わせ[C]
   → S4 世界[L] ─┐
   → S5 人物[L] ─┼→ S6 構造展開[C] → S7 出来事生成[L] ⇄ S8 整合確認[C+L] → S9 正本組み立て[C]
```

- S4 と S5 は S3 の結果だけに依存し、互いに独立して並行実行できる。
- 依存関係：スロット k の S7 は、同じ筋の直前のスロットの S8.judge に依存する（直前の出来事の結果を入力に使うため）。スロット k の比較相手は、実際に登場した人物（S7 の出力の `who`）で決まるため、コードタスク `S8.plan-e<k>` が、スロット k と時系列でそれより前のすべてのスロットの S7 の完了後に比較相手を決め、`S8.compare` と `S8.judge` を追加する。異なる筋の S7 は、この制約の範囲で並行実行できる。

## 2. 各段階

### 2.1 ID の体系

タスクカードの入力と、LLMタスクの出力の `sources` は、次のIDを使う。IDはすべてコードが振る。

| 対象 | 形式 | 例 | 振る段階 |
|---|---|---|---|
| 素材 | `m<3桁>` | `m003` | S1 |
| 入力由来の要素 | `<axis>:i<2桁以上>` | `want:i07` | S2 |
| 既定テーブルの要素 | `<axis>:t<行番号>` | `duty:t12` | テーブルの読み込み時 |
| 増補テーブルの要素 | `<axis>:x<行番号>` | `place:x4` | 追記時 |
| 世界セクション | `w<番号>` | `w2` | S4 |
| 人物 | `c<番号>` | `c1` | S3 |
| 出来事 | `e<3桁>` | `e005` | S6（スロットの作成時） |

各段階のカードには、その段階の入力に含めた対象のIDだけを列挙する。`sources_exist` は、そのカードに列挙したIDだけを正しいIDとして扱う。

### S0 入力取り込み [C]
- 入力：ナラティブまたは自由入力（[input.md](input.md)）、規模の指定（[scale.md](scale.md)）。
- 処理：個人情報の検出 → 正規化 → 規模の派生値の計算 → DAG の生成。
- 出力：`input.json`、manifest。

### S1 素材抽出 [L]
- タスクの単位：ナラティブの空でない1項目、または自由入力の1段落。
- 入力：その1項目の問いと回答（またはその1段落）だけ。
- 処理：回答から、物語の素材になる要素を、抽象化した短い語句（10〜30字）で5個抽出する。原文の表現をそのまま引用しない。断定や診断をしない。素材の種類は、heros-journey の分析の観点（切望＝desire、抑圧＝suppression、自己矛盾と葛藤＝conflict）と、world-building のコンテクストの観点（主題＝theme、雰囲気＝mood、心象＝image）を含む。
- 出力：`{"materials": [{"text": "...", "kind": "desire|fear|suppression|conflict|image|value|theme|mood"}], "sources": ["p001"]}`（materials は5件。sources はカードに示した入力のID：ナラティブの項目キー、または自由入力の段落ID `p<3桁>`）
- `share_across_runs: true`。

### S2 要素プール拡張 [L]
- タスクの単位：素材1個 × 要素の軸1つ（§3）。
- 入力：素材1個（ID つき）と、軸の定義文だけ。
- 処理：その素材から着想される、その軸の要素を5件、10〜40字で書く。加えて、その5件と対極にある要素を1件書く（heroes の「対になるキャラクター」を継承）。
- カードの規則には、heroes の生成規則を軸ごとに入れる（例：能力は、ありきたりな超能力を避け、発動の条件と制約を持たせる。願望は、具体的な人・場所・物・期限のいずれかを含める。役割は、現代の職能と空想の要素を組み合わせる）。軸ごとの規則の原本は `tables/element_axes.yaml` の `generation_rules` とし、カードには、そのタスクの軸の定義と規則だけを入力として示す（他の軸の規則を示さない：P1）。
- ありきたりな表現の一覧 `tables/cliches.yaml` を、入力スロットとしてカードに「使わない表現」として示し（タスク定義に一覧を書き写さない）、`avoid_listed` チェック（[task-model.md](task-model.md) §6.2）で検査する。
- 要素は、表層から深層まで、また軸ごとの観点（願望：身体的・精神的・社会的・超越的、役割：社会的・物語的・象徴的、など）に散らす（world-building Phase 1 の規則）。
- 出力：`{"items": ["..."], "counterpart": "...", "sources": ["m003"]}`
- コードは、NFKC 正規化・空白除去の後に重複する要素を除いて入力由来プールに加え、IDを振る。対極要素は `tables.lock` を取ってから、データディレクトリの増補テーブル `tables/<axis>.json` に追記する（[data-layout.md](data-layout.md) §2）。追記は、実行者の提出が合格したときだけ行い、キャッシュから `done` になったときは行わない。追記の前に、正規化後に同じ要素がテーブルにあれば追記しない。
- S2 のタスクは、S1 がすべて完了した後にコードタスク `S2.plan` が一度に作る。軸ごとのタスク数は `ceil(必要量 / 5) + 1` とし、素材を ID 順に巡回して割り当てる。すべての S2 タスクの完了後、コードタスク `S2.merge` が重複を除いて入力由来プールを作る。プールが必要量に満たない軸は、S3 でテーブル由来プールから補う（[scale.md](scale.md) §6）。
- `on_exhausted: skip`（失敗した拡張の分は、S3 でテーブル由来プールから補う）。
- `share_across_runs: true`。

### S3 組み合わせ [C]
- 入力：入力由来プール、既定テーブルと増補テーブル（以下、テーブル由来プール）、規模の派生値、プロット型テーブル、run の seed。
- 処理（すべて run の seed による）：
  1. 増補テーブルの軸ごとの行数を `table_snapshot` として manifest に記録する。以降、この行数までの行だけを使う。
  2. **入力由来の比率 r** を、一様分布 [0.5, 0.9] から決める。比率を固定しないのは、比率そのものを多様性の軸にするためである。r は manifest に記録する。
  3. プロット型を選ぶ。主筋に1つ（`--plot-type` の指定がある場合はそれを使う）、副筋と大河の各部にも1つずつ、主筋とは異なるものを選ぶ（同じ run の中で重複させない。候補が足りない場合だけ重複を許す）。長い物語が複数の型の組み合わせになるようにするためである。選べるプロット型は、そのフェーズで構造テンプレートが用意されているものに限る（§4）。
  4. 筋の数（[scale.md](scale.md) §6）と筋ごとの出来事数（§4.3）を決め、各筋の構造テンプレートを決める（§4.2）。
  5. 人物の数を決め（[scale.md](scale.md) §6）、役を割り当てる。役の割り当ての原本はこの手順である。
     - 主人公（`protagonist`）を必ず1人置く。主人公は1人だけとし、人物 ID は常に `c1` とする。
     - 次に、構造テンプレートの段階が要求する役（`messenger` 使者・`supporter` 支援者・`adversary` 敵対者）を、要求の多い順に1人ずつ割り当てる。
     - 残りの人物には、`messenger`・`supporter`・`adversary`・`bystander`（傍観者）から seed で役を選ぶ。役の重複を許す。
     - 人物の数が足りず割り当てられなかった役は「不在の役」として記録する（S6 で扱う）。
  6. 要素を割り当てる。各要素は、確率 r で入力由来プールから、確率 1−r でテーブル由来プールから、重複なしに選ぶ。
     - 各人物：`want`・`ability`・`duty`・`age`・`gender`・`species` を1つずつ
     - 主人公：`taboo` を1つ。加えて、入力由来の素材のうち種類が `suppression` のものがあれば、1つを「抑圧されている自己像」として割り当てる
     - 物語：`place`・`era`・`object` を1つずつ。加えて、入力由来の素材のうち種類が `theme` または `conflict` のものがあれば、1つを「解決すべき主題」として割り当てる
  7. 各人物に、名前の響き（§5）を1つ割り当て、その響きの音から6個を選ぶ。
- 出力：`assignment.json`（r、プロット型、筋と筋ごとの出来事数・構造テンプレート、cast の枠と役、不在の役、要素、音）。

### S4 世界 [L]
- タスクの単位：世界セクションの観点1つの1面（facet）、または一覧型のセクションの項目1件。生成するセクションは規模で決まり（[scale.md](scale.md) §6）、タスクの数は分量の配分（§8）で決まる。
- セクションのカタログは `tables/world_sections.yaml` を原本とする。各セクションは、定義文、観点の一覧（heros-journey と world-building の全観点・全小項目を取り込む。[lineage-inventory.md](../lineage-inventory.md) §10）、種類（`single`：本文1つ／`list`：項目を複数件）、本文の字数上限、前提セクション（最大2つ）を持つ。
- 一覧型のセクション（過去の出来事、社会集団、人々、未来のシナリオ）は、規模ごとの件数（`tables/scales.yaml` の `world_counts`）だけ、1件1タスクで生成する。未来のシナリオは楽観・悲観・中庸の3件とする。
- 入力：セクションの定義文と観点、物語の `place`・`era`、プロット型の名前、前提セクションの本文（一覧型は各項目の名前と1行の要約）。前提セクション以外の内容は渡さない。
- カードの手順に「物語の place・era の要素や前提セクションの文を言い換えて書き始めない。観点と切り口から書き始める」を加える。
- 同じセクションの面どうしで書き出し（先頭80字）が似すぎていないかを、コードタスク `S4.diversity-<section id>` が検査する（文字3-gram の Jaccard 係数が `tables/dedup.yaml` の `opening_threshold` 以上の組）。似すぎた面は、後から書かれた方を無効化し、次のカードの「前回の不合格理由」に、似ていた書き出しを避けるよう書く（無効化の上限に達した場合は警告を記録して採用する）。
- `single` のセクションは、観点ごとに、分量の配分で決めた数の面（facet）に分けて書く。各面には、コードが要素テーブルから異なる要素を1つずつ「切り口」として割り当てる（同じ観点の面どうしが同じ文の繰り返しにならないようにするため：P4）。
- 一覧型の項目にも、コードが異なる要素（年齢・役割・願望など）と、名前の響きの音を割り当てる。項目の名前は、与えた音から組み立てさせる（LLM の典型的な名前を避けるため：§5）。
- 出力：`single` の面は本文だけ（`output: text`、`extend_to_min: true`）。`list` の項目は、名前のタスク `S4.item_name`（`{"name": "...", "reading": "..."}`、与えた音を使う）と、本文のタスク `S4.item`（`output: text`、`extend_to_min: true`、入力に項目の名前を含む）に分ける。1タスクの字数は §8 の配分に従う。

### S5 人物 [L]
- タスクの単位：人物1人 × 項目1つ。項目は `name` → `profile` → `intro`・`motive`・`appearance`・`personality`・`values`・`backstory`（時期ごとに複数）・`relationships`（他の人物ごとに1件）・`voice`（口調と台詞の例）・`inner_conflict` → `catchphrase` の順に依存する。各項目の字数は §8 の配分に従う。
- 主人公以外の人物の項目には、主人公の文脈として、主人公の名前と役を入力に含める。`motive`・`catchphrase` では、主人公の `intro` も含める。主人公の割り当て要素・禁忌・抑圧されている自己像は、主人公自身の項目にだけ入力する（P1）。
- すべての項目の入力に、その人物の役の定義文（`tables/roles.yaml`。heros-journey・world-building の4役の定義を取り込む）と、プロット型の `character_requirements` を含める。
- `name`：入力は、S3 で割り当てた音6個と、名前の響きの説明文だけ。出力は `{"name": "...", "reading": "カタカナの読み", "sources": ["<響きの集合のID>"]}`。検証：`reading` が、与えた音のうち2個以上を含む（`uses_given`）。
- `profile`：入力は、その人物の名前・役・割り当て要素（主人公は `taboo` を含む）。
- 長い項目（profile・appearance・personality・values・backstory・relationship・voice・inner_conflict）は `output: text`、`extend_to_min: true` とし、本文だけを書かせる。短い項目（name・intro・motive・catchphrase）は JSON のままとする。
- `motive`：入力は、その人物の名前・役・プロフィールと、他の人物の名前・役だけ。出力は `{"motive": "...", "sources": [...]}`（120字以内）。主人公に「抑圧されている自己像」が割り当てられていれば、入力に含める。
- `intro`：短い紹介（50字以内で、文末記号で終わる1文。world-building の short_introduction）。`ends_complete` で検査する。
- `appearance`：外見と魅力（年齢・性別・種族・体格・装い。150字以内。heroes・heros-journey の外見の項目）。
- `catchphrase`：決め台詞（一人称で始まる1文。heroes の catchphrase）。

### S6 構造展開 [C]
- 入力：`assignment.json`、構造テンプレート、プロット型。
- 処理：
  1. （筋ごとの出来事数は S3 で決定済み）
  2. 各筋の出来事数を、その筋のテンプレートの段階に配分する。各段階に最低1件を割り当て、残りは段階の重みに比例して配分する（端数は seed で決める）。
  3. 副筋のスロットを、主筋の段階の間に seed で配置する。大河では、部を番号の順に並べ、部の間や部の中に他の部のスロットを差し込まない。これにより、全スロットの時系列の順序が決まる。
  4. プロット型の必須の出来事（§4.1）を、指定された段階のスロットに割り当てる。
  5. 各スロットに、登場させる人物を割り当てる。段階が要求する役の人物を必ず含め（同じ役の人物が複数いる場合は seed で選ぶ）、ほかに0〜2人を seed で加える。要求する役が「不在の役」の場合、人物は割り当てず、段階の `absent_role_note`（例：「敵対者は、人物ではなく状況や内面の力として現れる」）をスロットに付ける。
  6. 段階に `object: true` が付いている場合、スロットに物語の `object` を付ける。
  7. 各スロットに、世界の抜粋に使うセクションを決める：段階の `world_sections` に挙げられたセクションのうち、この run で生成したものを最大2つ、挙げられた順に選ぶ。1つもない場合は「場の描写」を使う。
- 出力：`slots.json`。S7 のタスクをスロットの数だけ生成する。

### S7 出来事生成 [L]
- タスクの単位：スロット1つ。`candidates: 3`、`select_candidate: least_similar`（Phase 1 は `candidates: 1`）。
- 入力：
  - スロットの段階の定義文。割り当てられていれば、プロット型の必須の出来事の説明、`absent_role_note`、`object`
  - そのスロットに割り当てた人物の ID・名前・役・動機
  - S6 で選んだ世界セクションの body（最大2件）
  - 同じ筋の直前の出来事の `result` だけ（それ以前の出来事は渡さない）
  - その筋のプロット型の `conflict`。段階がクライマックスに当たる場合（段階の `climax: true`）は `climax` も
  - 物語の「解決すべき主題」（割り当てられていれば）
- 出力：`{"when": "", "where": "", "who": ["c1"], "why": "", "intent": "", "what": "", "result": "", "emotion": "", "foreshadowing": "", "sources": [...]}`
  - `intent`：人物の意思（world-building の protagonist_actions の「意思」）、`emotion`：出来事で人物が受ける感情（受動的な感情）、`foreshadowing`：後の出来事への伏線（実行者はすべてのスロットで書く。筋の最後のスロットの伏線は、S9 がコードで空にする。最後かどうかをカードに示さないため：P1）
- 検証：各項目120字以内、`who` は入力の人物IDの部分集合（`ids_subset`）。

### S8 整合確認 [C+L]
- [C] `who` と `sources` の実在、各項目の字数。
- [L] 矛盾の確認。1回の確認は、2つの記述だけを入力とする別のタスク `S8.compare-<スロット>-k<n>`（kind: llm）とする。
  - 矛盾とは、2つの記述が事実として両立しないことだけを指す（同じ人物が同時に別の場所にいる、記述Aで確定した結果を記述Bが理由なく覆す、存在しないはずの人物・物が現れる、など）。人物の心情・関係・状況の変化や展開は矛盾に含めない。カードにこの定義を示す。
  - 質問：「記述Bは、記述Aの結果と矛盾しますか」→ `{"answer": "yes|no", "reason": "1文", "sources": ["<記述AのID>", "<記述BのID>"]}`
  - スロットごとのコードタスク `S8.judge-<スロット>` が、そのスロットの compare の結果をまとめ、`yes` があれば S7 を無効化する。
  - 記述Aとして比較する出来事：(a) 同じ筋の直前の出来事、(b) スロット k の S7 の出力の `who` の各人物が、時系列でそれより前に `who` として登場した直近の出来事（(a) と同じものは除く）。比較相手は `S8.plan` が S7 の出力から決める。S7 が無効化されて再生成された場合は、`S8.plan` も依存により再実行され、比較相手を決め直す。1スロットあたり最大3件とし、(b) が多い場合は時系列で近いものを優先する。
- いずれかが `yes` の場合、そのスロットの S7 を無効化する（[task-model.md](task-model.md) §4.3）。候補生成をしている場合は、すべての候補タスクと、候補を選んだコードタスクをまとめて無効化する。S7 の `max_invalidations` は2とする。上限に達した後も矛盾ありと判定された場合は、S7 を失敗にせず、最後の出力を採用して manifest の `warnings` に記録する（無人で完走させるため。整合確認は品質の検査であり、物語の成立を止める条件ではない）。

### S7.detail 場面の詳述 [L]
- タスクの単位：出来事1件の場面（beat）1つ。出来事ごとの場面の数は §8 の配分で決める。場面の働き（発端・展開・転換・余韻など）は、コードが `tables/beats.yaml` から割り当てる。
- 依存：そのスロットの `S8.judge`（整合確認の後に詳述する）と、同じ出来事の直前の場面。
- 入力：出来事の記述（when・where・who・why・intent・what・result・emotion）、場面の働き、登場人物の名前・役・紹介・口調、S6 で選んだ世界の抜粋、同じ出来事の直前の場面の末尾（コードが600字を切り出す）。他の出来事の場面は渡さない。
- 出力：場面の説明的な記述（`output: text`、`extend_to_min: true`。三人称で、いつ・どこで・誰が・何をしたかが分かる書き方。小説の文体ではなく、正本としての説明的な記述）。字数は §8 の配分に従う。

### S9 正本組み立て [C]
- 入力：S3〜S8 の出力。
- 処理：
  1. 正本（§6）を組み立てる。`story.md` は、出来事ごとに、要約の1文（「いつ、どこで、誰が、何のために、何をして、どうなったか」の文型）と、その出来事の場面の詳述を時系列の順に並べる。`characters.md` は人物ごとの全項目、`world.md` は世界の全セクション・全項目を並べる。
  2. 文型に差し込む値は、末尾の句読点（「。」「、」）と、`why` の末尾の「ため」「から」「ために」を取り除いてから差し込む（「〜ためために」のような重複を防ぐ）。役は日本語の名前（`tables/roles.yaml` の `name`）で表示する。
  3. 分量（§8）を集計し、最低ラインに満たない資料があれば manifest の `warnings` に記録する。
  4. run がバッチに属する場合、重複除外とバッチの補充（§7）を行う。

## 4. プロット型と構造テンプレート

### 4.1 プロット型

- `tables/plot_types.yaml` に、heros-journey の21型を置く。各型は次を持つ。これらは開発者がテーブルとして記述し、実行時に LLM に生成させない。
  - `id`, `name`, `core`（中核の構造、1文）
  - `required_events`：必須の出来事の一覧（説明と、割り当てる段階）
  - `structure`：`standard`、または専用テンプレートのID
  - `character_requirements`（登場人物の要件）、`time_design`（時間の設計）、`conflict`（葛藤の種類）、`climax`（クライマックスの条件）、`pacing`（ペース配分）、`typical_setting`（典型的な舞台）：heros-journey と world-building のプロット型の項目を取り込む。各1〜2文
- `structure: standard` の型が14型、専用テンプレートを持つ型が7型ある。型の一覧は `tables/plot_types.yaml` を原本とする。専用テンプレートを持つのは、段階構造に押し込むと個性が失われて中庸に収斂する型（タイムループ、断片的構成など）である（P4）。

### 4.2 構造テンプレートの選び方

- 構造テンプレートは `tables/structures.yaml` に置く。各テンプレートは段階の一覧を持ち、各段階は次を持つ：定義文、指針（heros-journey の段階ごとの指針と、骨子 A〜E の要素：予兆・挫折・代償など）、幕（`act`）、重み、要求する役、`absent_role_note`、`world_sections`、`object`（真偽値）、`climax`（真偽値）。
- 標準の構造テンプレートは3つある：`three-beat`（3段階）、`kishotenketsu`（4段階）、`heros-journey-12`（12段階）。段階の定義は `tables/structures.yaml` を原本とする。
- 主筋（および大河の各部の主筋）のテンプレートは、プロット型が `standard` の場合、その筋に配分された出来事数で決める。

| 筋の出来事数 | テンプレート |
|---|---|
| 5以下 | `three-beat` |
| 6〜11 | `kishotenketsu` |
| 12以上 | `heros-journey-12` |

- プロット型が専用テンプレートを持つ場合は、出来事数によらずそれを使う。専用テンプレートは、段階の繰り返し・省略の規則によって、任意の出来事数に対応する。
- 副筋は常に `kishotenketsu` を使い、その副筋に割り当てたプロット型の必須の出来事を、`kishotenketsu` の段階に割り当てる（プロット型の各必須の出来事は、標準の3テンプレートそれぞれについて割り当てる段階を持つ）。

### 4.3 筋への出来事数の配分

- 副筋1本あたりの出来事数は、4〜6件を seed で決める。
- 主筋の出来事数 = 全体の出来事数 − 副筋の出来事数の合計。
- 大河では、部ごとに出来事数を決め（[scale.md](scale.md) §4）、各部を1本の主筋として扱う。大河の部に副筋は置かない。
- 主筋の出来事数が3未満にならないよう、出来事数の下限に副筋の分を含める（[scale.md](scale.md) §4）。

## 5. 名前の生成

LLM に名前を自由に作らせると、内部知識の典型的な名前に偏る（P4）。名前は、コードが与えた音から組み立てさせる。

- `tables/name_sounds.yaml` に、名前の響きの集合を置く。各集合は、響きの説明文（例：「硬い子音が多く、短い」）と、音（カタカナの音節）の一覧を持つ。特定の実在の言語・民族を指す名前は付けない。
- S3 が、各人物に響きの集合を1つ、その中から音を6個、seed で割り当てる。
- S5 `name` は、与えられた音のうち2個以上を使って名前を作る。

## 6. 正本

- `story.json`：形式は `schemas/story.schema.json` を原本とする（P1-11 で作成）。次を持つ：`meta`（run ID、seed、規模、入力由来の比率、筋ごとのプロット型、構造テンプレート、入力の種類、解決すべき主題）、`world`（世界セクションと一覧型の項目）、`cast`（人物：役、名前、読み、紹介、プロフィール、動機、外見、決め台詞、割り当て要素）、`threads`（筋：主・副、部、プロット型）、`events`（出来事：段階、筋、when・where・who・why・intent・what・result・emotion・foreshadowing、sources）。すべての要素に §2.1 のIDと `sources` を持たせる。
- `story.md`：`story.json` からテンプレートで生成する説明文。

## 7. 重複除外とバッチの補充

- 指紋：cast の名前・プロフィールと、events の全項目を、NFKC 正規化・空白除去・小文字化した上で連結し、sha256 をとる。指紋が同じバッチ内の既存の正本と一致すれば重複とする。
- 近似重複：events の `what` と `result` を連結した文字列の、文字3-gram の Jaccard 係数が、同じバッチ内の既存の正本のいずれかと閾値以上であれば近似重複とする。閾値は `tables/dedup.yaml` を原本とする（初期値 0.5）。
- 重複・近似重複の run は `duplicate` とし、バッチの要求件数に数えない。
- 補充：`st new --count N` は、最初に N 本の run を作る。S9 は `batch.lock` を取ってバッチの manifest を更新する。その run が `duplicate` になった場合に限り、作成数が上限 `max(3N, N+10)` に達していなければ、次の index の run を1本作る（heros-journey を継承）。これにより、`duplicate` 以外で終わる run の数は N を超えない。

## 8. 分量の配分

[ADR-0007](../adr/0007-volume-floor.md) の最低ラインを満たすよう、コードが run の作成時（S0）とタスクの追加時（S3・S6）に、タスクの数と1タスクの字数を決める。

| 資料 | 最低ライン（規模倍率1の場合） | 満たし方 |
|---|---|---|
| 人物 | 合計10,000字 | 人物ごとの項目（S5）の字数の合計。主人公に多く、他の人物に少なく配分する（重みは `tables/volume.yaml`） |
| 世界 | 100,000字 | 生成するセクションの観点ごとの面（facet）の数と、一覧型の項目の数（S4） |
| 物語 | 100,000字 | 出来事ごとの場面（beat）の数（S7.detail） |

- 1タスクの字数の目安は、`tables/volume.yaml` に項目ごとに定める（例：場面 1,500〜2,500字、世界の面 800〜1,500字、人物の項目 300〜1,500字）。目安の下限を `min_chars`、上限を `max_chars` の検査に使い、カードにも目安を示す。
- タスクの数 = ceil(資料の目標字数 ÷ 1タスクの目安の中央値)。目標字数 = 最低ライン × 規模の倍率（`tables/scales.yaml` の `volume_multiplier`。掌編・短編 1、中編 2、長編 4、大河 8 を初期値とする）。
- 配分の結果は manifest の `scale.derived.volume` に記録する。
- S9 は実際の字数を集計し、最低ラインに満たない場合は警告を記録する（run は止めない）。

## 9. 事実の層と用語集

世界と人物の資料は、**事実の層**と**描写の層**の2層で作る。事実の層は、具体的・明示的で、誰が読んでも同じ世界を想起できる、客観性と再現性のある情報である。描写の層は、事実に従って書く情感のある記述である。事実の層を先に作り、描写の層の入力に渡す。

### 9.1 用語集（固有名詞の登録）
- 地名・組織名・用語・人名などの固有名詞は、すべて用語集に登録してから使う。用語集の項目は、ID、名前、読み、種類（地名・組織・用語・人物など）、1文の定義、登録したタスクを持つ。
- 用語集は専用のファイルに保存せず、`done` のタスクの出力から決定的に組み立てる。登録のしかた：
  - S5.name と S4.item_name の出力は、コードが登録する。種類は、S5.name なら「人物」、S4.item_name なら項目が属するセクションの名前。定義は、S5.name なら「<役の日本語名>」、S4.item_name なら「<セクションの名前>の項目」とする。
  - S4.facts の出力の `glossary`（名前・読み・種類・定義）は、そのまま登録する。
- ID は `g` に、`sha256("<登録したタスクのID>:<出力の中の順番>")` の16進の先頭6桁を続けたもの（例：`g3fa91c`）とする。後からタスクが追加されても、既存の ID は変わらない。衝突した場合は、組み立て時にエラーとして記録する。
- 固有名詞の名前は、コードが割り当てた名前の響きの音（§5）から組み立てさせる。
- 以降のタスクのカードには、そのタスクに関係する用語集の項目（入力に現れる ID の項目と、同じセクションの項目）だけを示す。
- `no_new_proper_nouns` は、「未登録の固有名詞を持ち込まない」検査として扱う。候補のうち、用語集とカードの入力に含まれるものは除外する。描写の層のタスクでは `mode: fail` とする。

### 9.2 世界の事実（S4.facts）
- タスクの単位：世界セクションの観点1つ。描写の面（S4.section）より先に実行する。
- 項目は、セクションの観点ごとに `tables/world_sections.yaml` の `fact_schema` で定める。数値・単位・年代・件数・名前を必須の項目とし、曖昧な語（「多い」「古い」など）では埋められないようにする。例：
  - 地理：面積（km²）、標高（m）、主要な地点とその間の距離（km）、季節ごとの平均気温（℃）と降水量（mm）、資源の種類と産出量
  - 社会：制度・組織の名前、権限、構成員の数、規則の条文（番号つき）、通貨の名前と単位、暦
  - 歴史：年表（年、出来事、原因、結果、関係する用語集の項目）
  - 人々：人口、年齢構成、職業の分布、言語
- 出力は JSON（`fact_schema` に従う）。新しい固有名詞は、出力の `glossary` に（名前・読み・種類・定義を）書かせ、コードが用語集に登録する。
- 一覧型のセクション（過去の出来事、社会集団、人々、未来のシナリオ）の各項目も、本文の前に事実の項目（年・規模・構成・所属など）を持つ。
- S4.section（描写の面）の入力には、その観点の事実と、関係する用語集の項目を含め、手順に「事実と矛盾させない。事実にない数値・固有名詞を加えない」を加える。
- 同じセクションの観点は、割り当ての順に1つずつ実行する（各 S4.facts は、同じセクションの直前の観点の S4.facts に依存する）。前提の事実（`prerequisite_facts`）には、前提セクションの事実に加えて、同じセクションの先行する観点の事実を含める。手順に「前提の事実と同じ量（標高・面積・人口など）を書くときは、同じ値を使う」を加える。セクションどうしは、これまでどおり並行して実行できる。
- 出典：`default_sources` に物語の素材（場所・時代）の ID を指定する。不明な出典 ID は除いて警告とし、有効な出典が残らなければ既定の出典で補う（task-model §6.2 の `sources_exist` の扱い）。出力例の `sources` には実在しない ID を書かない。
- 用語集の名前の響きの検査（読みが与えられた音を2個以上使うこと）に合わない `glossary` の項目は、再試行の理由にせず、その項目を除いて警告とする。事実の行は残す。

#### 世界の暦（S4.calendar）
- タスクの単位：run に1つ。S3.assign の後、すべての S4.facts と S5.facts より先に実行する。
- 出力（JSON）：暦の名前、読み、定義（1文）、紀元の出来事（1文）、現在の年（1以上の整数）。暦の名前は固有名詞として名前の響きの検査を受け、コードが用語集に種類「暦」で登録する。物語の時代の素材を入力に含め、紀元の出来事はそれと矛盾させない。
- 現在の年は、物語が始まる年とする。
- コードによる統一：S4.facts と S5.facts の入力に暦（名前・現在の年）を含める。出力の `calendar` は、モデルの値にかかわらずコードが暦の名前に置き換え、異なっていた場合は警告とする。
- 年の範囲：S4.facts の `year` は1以上、現在の年以下とする。ただし未来のシナリオのセクションでは、現在の年より大きくてよい。S5.facts の年表の年は生年以上、現在の年以下とする。範囲外は再試行の理由とする。
- S5.facts の `age` は、コードが「現在の年 − 生年」に置き換え、異なっていた場合は警告とする。

### 9.3 人物の事実（S5.facts）
- タスクの単位：人物1人。`name` の後、他の項目より先に実行する。
- 項目：年齢、生年（物語の暦）、身長（cm）、体格、出身地（用語集）、居住地（用語集）、職業、所属（用語集）、家族構成（続柄と名前）、年表（年、出来事）、技能（能力の要素を具体化したもの）。
- 人物の他の項目（profile など）の入力に事実のシートを含め、事実と矛盾させない。

### 9.4 出力
- S9 は、`world_facts.md`（世界の事実を、表と年表で）、`glossary.md`（用語集）、`world.md`（描写）、`characters.md`（人物ごとに、事実のシートの後に描写）を出力する。
- 事実の層の字数は、世界・人物の分量（§8）に含める。

## 10. 生成物の品質の検査

実機の生成で見つかった問題に対して、次の検査をコードで行う。

| 検査 | 内容 | 不合格のときの扱い |
|---|---|---|
| `no_copy_from_inputs` | 出力と、カードの入力の本文との最長共通部分文字列が、`tables/dedup.yaml` の `max_copy_chars`（初期値 60字）以上 | 不合格（理由に写した部分を示す） |
| 継続の重複の除去 | 継続で連結するとき、既出の段落と同一、または文字3-gram の Jaccard 係数が 0.8 以上の段落を取り除く | 取り除いて警告を記録 |
| `avoid_listed`（作り方の語） | 出力に、作り方の情報を表す語（`tables/meta_terms.yaml`：「名前の響き」「プロット型」「切り口」「タスク」「カード」「枠組みで進行」など）が含まれる | 不合格 |

- カードの「入力」節では、物語の素材（要素・事実・用語集・前の出来事など）と、作り方の指示（名前の響き・切り口の役割など）を、見出しで区別して示す。作り方の指示は、出力に書かないことを手順に明記する。
- S9 の要約文は、文の継ぎ合わせをやめ、「いつ／どこで／誰が／目的／行動／結果」を項目として並べる書式にする。
- 物語の分量の配分では、場面の数を、1場面の字数の目安の**下限**で割って求める（小さいモデルが目安より短く書く傾向を見込むため）。
