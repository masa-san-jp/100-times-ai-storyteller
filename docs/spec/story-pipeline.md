# spec: 物語生成ハーネス

- 所有範囲：S0〜S9 の各段階の入力・処理・出力、素材と要素のID、要素の軸とプール、プロット型と構造テンプレート、名前の生成、正本の構成、重複除外とバッチの補充

`[C]` はコードタスク、`[L]` はLLMタスクを表す。`[C+L]` の段階は、LLMタスクとそれを受けるコードタスクの2種類のタスクで構成する。
LLM タスク1つは1つの要素だけを作る（P1、[task-model.md](task-model.md) §2.5）。出典（`sources`）は LLM に書かせず、カードに示した素材の ID をコードが記録する（P3、task-model §6.6）。タスク定義の形式は [task-model.md](task-model.md) による。
この文書に書いた各タスクの数値（候補数・字数・件数・共有の有無）は初期値である。タスク定義（`harness/story/tasks/*.yaml`）を作成した時点で、そのタスク定義が原本になり、この文書の数値はタスク定義へのリンクに置き換える（[docs/README.md](../README.md) §2.1）。

## 1. 全体の流れ

```
S0 入力取り込み[C] → S1 素材抽出[L] → S2 要素プール拡張[L] → S3 組み合わせ[C]
   → S4 世界[L] ─┐
   → S5 人物[L] ─┼→ S6 構造展開[C] → S7 出来事生成[L] ⇄ S8 整合確認[C+L] → S9 正本組み立て[C]
```

- S4 と S5 は S3 の結果だけに依存し、互いに独立して並行実行できる。
- 依存関係：スロット k の S7 は、同じ筋の直前のスロットの S8.judge に依存する（スロット k の最初の項目 `what` が依存する）（直前の出来事の結果を入力に使うため）。スロット k の比較相手は、登場する人物（S6 が割り当てた `who`）で決まる。コードタスク `S8.plan-e<k>` が、スロット k と時系列でそれより前のすべてのスロットの S7 の完了後に比較相手を決め、`S8.compare` と `S8.judge` を追加する。異なる筋の S7 は、この制約の範囲で並行実行できる。

## 2. 各段階

### 2.1 ID の体系

タスクカードの入力と、コードが記録する出典（`sources`）は、次のIDを使う。IDはすべてコードが振る。

| 対象 | 形式 | 例 | 振る段階 |
|---|---|---|---|
| 素材 | `m<3桁>` | `m003` | S1 |
| 入力由来の要素 | `<axis>:i<2桁以上>` | `want:i07` | S2 |
| 既定テーブルの要素 | `<axis>:t<行番号>` | `duty:t12` | テーブルの読み込み時 |
| 増補テーブルの要素 | `<axis>:x<行番号>` | `place:x4` | 追記時 |
| 世界セクション | `w<番号>` | `w2` | S4 |
| 人物 | `c<番号>` | `c1` | S3 |
| 出来事 | `e<3桁>` | `e005` | S6（スロットの作成時） |

各段階のカードには、その段階の入力に含めた対象のIDだけを列挙する。コードは、そのカードに列挙したIDを出典として記録する。

### S0 入力取り込み [C]
- 入力：ナラティブまたは自由入力（[input.md](input.md)）、規模の指定（[scale.md](scale.md)）。
- 処理：個人情報の検出 → 正規化 → 規模の派生値の計算 → DAG の生成。
- 出力：`input.json`、manifest。

### S1 素材抽出 [L]
- タスクの単位：ナラティブの空でない1項目、または自由入力の1段落。
- 入力：その1項目の問いと回答（またはその1段落）だけ。
- タスクの単位はさらに、素材1個ずつに分ける（`S1.extract-p<3桁>-<1〜5>`、`element: labeled`）。本番では同じ項目・段落の5個を順に実行し、先に抽出した素材をカードに「すでに抽出した素材（重ねない）」として示す。 開発用 `dev` の件数は [scale.md](scale.md)「開発用の規模 `dev`」による。
- 処理：回答から、物語の素材になる要素を1つ、抽象化した短い語句（10〜30字）で抽出し、種類を1つ付ける。原文の表現をそのまま引用しない。断定や診断をしない。素材の種類は、heros-journey の分析の観点（切望＝desire、抑圧＝suppression、自己矛盾と葛藤＝conflict）と、world-building のコンテクストの観点（主題＝theme、雰囲気＝mood、心象＝image）を含む。
- 出力：`{"text": "...", "kind": "desire|fear|suppression|conflict|image|value|theme|mood"}`。出典は、コードがカードに示した入力のID（ナラティブの項目キー、または自由入力の段落ID `p<3桁>`）を記録する。試行の上限に達した素材は `on_exhausted: skip` とする。
- `share_across_runs: true`。

### S2 要素プール拡張 [L]
- タスクの単位：素材1個 × 要素の軸1つ（§3）。
- 入力：素材1個（ID つき）と、軸の定義文だけ。
- 処理：その素材から着想される、その軸の要素を5件、10〜40字で書く。加えて、その5件と対極にある要素を1件書く（heroes の「対になるキャラクター」を継承）。
- 1回の推論で1件を作る（`element: text`）。要素のタスク `S2.expand-m<3桁>-<axis>-<1〜5>` を順に実行し、先に書いた要素をカードに「すでに書いた要素（重ねない）」として示す。対極のタスク `S2.counter-m<3桁>-<axis>` は5件の完了後に実行し、5件を入力とする。
- カードの規則には、heroes の生成規則を軸ごとに入れる（例：能力は、ありきたりな超能力を避け、発動の条件と制約を持たせる。願望は、具体的な人・場所・物・期限のいずれかを含める。役割は、現代の職能と空想の要素を組み合わせる）。軸ごとの規則の原本は `tables/element_axes.yaml` の `generation_rules` とし、カードには、そのタスクの軸の定義と規則だけを入力として示す（他の軸の規則を示さない：P1）。
- ありきたりな表現の一覧 `tables/cliches.yaml` を、入力スロットとしてカードに「使わない表現」として示し（タスク定義に一覧を書き写さない）、`avoid_listed` チェック（[task-model.md](task-model.md) §6.2）で検査する。
- 要素は、表層から深層まで、また軸ごとの観点（願望：身体的・精神的・社会的・超越的、役割：社会的・物語的・象徴的、など）に散らす（world-building Phase 1 の規則）。
- 出力：要素1件の本文だけ（対極のタスクも同じ）。
- コードは、NFKC 正規化・空白除去の後に重複する要素を除いて入力由来プールに加え、IDを振る。対極要素は `tables.lock` を取ってから、データディレクトリの増補テーブル `tables/<axis>.json` に追記する（[data-layout.md](data-layout.md) §2）。追記は、実行者の提出が合格したときだけ行い、キャッシュから `done` になったときは行わない。追記の前に、正規化後に同じ要素がテーブルにあれば追記しない。
- S2 のタスクは、S1 がすべて完了した後にコードタスク `S2.plan` が一度に作る。軸ごとの組（素材 × 軸。要素5件と対極1件）の数は `ceil(必要量 / 5) + 1` とし、素材を ID 順に巡回して割り当てる。すべての S2 タスクの完了後、コードタスク `S2.merge` が重複を除いて入力由来プールを作る。プールが必要量に満たない軸は、S3 でテーブル由来プールから補う（[scale.md](scale.md) §6）。開発用 `dev` の素材数・候補倍率・余分な組を作らない扱いは [scale.md](scale.md)「開発用の規模 `dev`」による。
- `on_exhausted: skip`（失敗した要素の分は、S3 でテーブル由来プールから補う。1件の失敗は、同じ組の他の要素を止めない）。
- `share_across_runs: true`。

### S3 組み合わせ [C]
- 入力：入力由来プール、既定テーブルと増補テーブル（以下、テーブル由来プール）、規模の派生値、プロット型テーブル、run の seed。
- 処理（すべて run の seed による）：
  1. 増補テーブルの軸ごとの行数を `table_snapshot` として manifest に記録する。以降、この行数までの行だけを使う。
  2. **入力由来の比率 r** を、一様分布 [0.5, 0.9] から決める。比率を固定しないのは、比率そのものを多様性の軸にするためである。r は manifest に記録する。
  3. プロット型を選ぶ。主筋に1つ（`--plot-type` の指定がある場合はそれを使う）、副筋と大河の各部にも1つずつ、主筋とは異なるものを選ぶ（同じ run の中で重複させない。候補が足りない場合だけ重複を許す）。長い物語が複数の型の組み合わせになるようにするためである。選べるプロット型は、そのフェーズで構造テンプレートが用意されているものに限る（§4）。
  4. 筋の数（[scale.md](scale.md) §6）と筋ごとの出来事数（§4.3）を決め、各筋の構造テンプレートを決める（§4.2）。
  5. 人物の数を決め（[scale.md](scale.md) §6）、役を割り当てる。役の割り当ての原本はこの手順である。
     - 主人公（`protagonist`）を必ず1人置く。主人公は1人だけとし、人物 ID は常に `c1` とする。
     - 次に、構造テンプレートの段階が要求する役（`messenger` 使者・`supporter` 支援者・`adversary` 敵対者）を、要求の多い順に1人ずつ割り当てる。
     - 残りの人物には、`messenger`・`supporter`・`adversary`・`bystander`（傍観者）から seed で役を選ぶ。役の重複を許す。
     - 人物の数が足りず割り当てられなかった役は「不在の役」として記録する（S6 で扱う）。
  6. 要素を割り当てる。各要素は、確率 r で入力由来プールから、確率 1−r でテーブル由来プールから、重複なしに選ぶ。
     - 各人物：`want`・`ability`・`duty`・`age`・`gender`・`species` を1つずつ
     - 主人公：`taboo` を1つ。加えて、入力由来の素材のうち種類が `suppression` のものがあれば、1つを「抑圧されている自己像」として割り当てる
     - 物語：`place`・`era`・`object` を1つずつ。加えて、入力由来の素材のうち種類が `theme` または `conflict` のものがあれば、1つを「解決すべき主題」として割り当てる
  7. 各人物に、名前の響き（§5）を1つ割り当て、その響きの音から6個を選ぶ。
- 出力：`assignment.json`（r、プロット型、筋と筋ごとの出来事数・構造テンプレート、cast の枠と役、不在の役、要素、音）。

### S4 世界 [L]
- 開発用 `dev` の事実の範囲は [scale.md](scale.md)「開発用の規模 dev」による。生成した事実の型・参照・意味の検証は本番と同じとする。
- タスクの単位：世界セクションの観点1つの1面（facet）、または一覧型のセクションの項目1件。生成するセクションは規模で決まり（[scale.md](scale.md) §6）、タスクの数は分量の配分（§8）で決まる。
- セクションのカタログは `tables/world_sections.yaml` を原本とする。各セクションは、定義文、観点の一覧（heros-journey と world-building の全観点・全小項目を取り込む。[lineage-inventory.md](../lineage-inventory.md) §10）、種類（`single`：本文1つ／`list`：項目を複数件）、本文の字数上限、前提セクション（最大2つ）を持つ。
- 一覧型のセクション（過去の出来事、社会集団、人々、未来のシナリオ）は、規模ごとの件数（`tables/scales.yaml` の `world_counts`）だけ、1件1タスクで生成する。未来のシナリオは楽観・悲観・中庸の3件とする。
- 入力：セクションの定義文と観点、物語の `place`・`era`、プロット型の名前、前提セクションの本文（一覧型は各項目の名前と1行の要約）。前提セクション以外の内容は渡さない。
- カードの手順に「物語の place・era の要素や前提セクションの文を言い換えて書き始めない。観点と切り口から書き始める」を加える。
- 同じセクションの面どうしで書き出し（先頭80字）が似すぎていないかを、コードタスク `S4.diversity-<section id>` が検査する（文字3-gram の Jaccard 係数が `tables/dedup.yaml` の `opening_threshold` 以上の組）。似すぎた面は、後から書かれた方を無効化し、次のカードの「前回の不合格理由」に、似ていた書き出しを避けるよう書く（無効化の上限に達した場合は警告を記録して採用する）。
- `single` のセクションは、観点ごとに、分量の配分で決めた数の面（facet）に分けて書く。各面には、コードが要素テーブルから異なる要素を1つずつ「切り口」として割り当てる（同じ観点の面どうしが同じ文の繰り返しにならないようにするため：P4）。
- 一覧型の項目にも、コードが異なる要素（年齢・役割・願望など）と、名前の響きの音を割り当てる。項目の名前は、与えた音から組み立てさせる（LLM の典型的な名前を避けるため：§5）。
- 出力：`single` の面は本文だけ（`output: text`、`extend_to_min: true`）。`list` の項目は、名前のタスク `S4.item_name`（`{"name": "...", "reading": "..."}`、与えた音を使う）と、本文のタスク `S4.item`（`output: text`、`extend_to_min: true`、入力に項目の名前を含む）に分ける。1タスクの字数は §8 の配分に従う。

- 世界の描写の生成には、今回の観点または一覧型の当該項目の事実とその参照先を渡す。参照先に含まれる前提の事実も入力に保ち、確定事実を変更しない。生成カードは文字数予算に収め、同じセクションの全事実は後続の整合検査で使う。
- 描写の後、`S4.consistency` が最大6行の確定事実と描写本文だけで矛盾の有無を判定する（判定と理由1つ）。`single` は同じセクションの全事実と参照先、`list` は当該項目の事実と参照先を元の順で最大6行ずつに分割し、すべての分割を検査する。矛盾の理由には確定した値と食い違う記述を具体的に書き、再生成のカードに渡す。数値だけでなく、制度・種類・成立条件などの意味の食い違いを含め、言及がないことは矛盾にしない。 比較する事実と描写は、同じ対象・属性について両立しない場合だけ矛盾とする。種類が近いという理由や名称・数値の違いだけで、別の行事・手続・対象を同一視しない。分割に対応する事実がない記述を、他の対象の事実で補って矛盾としない。ただし、描写による明示的な同一視・否定・唯一性などで確定事実と両立しなくなる場合、同じ対象の名称・数値の違い、制度・成立条件の意味違反は引き続き検査する。
- 描写ごとのコードタスク `S4.consistency_judge` は、すべての判定を待ち、矛盾ありなら当該描写だけを無効化する。再生成は `max_invalidations` までとし、上限でも矛盾する描写は `skipped` にして失敗報告と警告を残す。判定の省略は警告とともに扱い、確認できなかった描写も未定とする。前提描写を使うタスク・多様性検査・S6 は、この検査の完了を待つ。

### S5 人物 [L]
- 開発用 `dev` の家族・年表・技能の反復件数は [scale.md](scale.md)「開発用の規模 dev」による。scalar 事実の全項目と、生成した事実の型・参照・意味の検証は本番と同じとする。
- タスクの単位：人物1人 × 項目1つ。項目は `name` → `profile` → `intro`・`motive`・`appearance`・`personality`・`values`・`backstory`（時期ごとに複数）・`relationships`（他の人物ごとに1件）・`voice`（口調と台詞の例）・`inner_conflict` → `catchphrase` の順に依存する。各項目の字数は §8 の配分に従う。
- 主人公以外の人物の項目には、主人公の文脈として、主人公の名前と役を入力に含める。`motive`・`catchphrase` では、主人公の `intro` も含める。主人公の割り当て要素・禁忌・抑圧されている自己像は、主人公自身の項目にだけ入力する（P1）。
- すべての項目の入力に、その人物の役の定義文（`tables/roles.yaml`。heros-journey・world-building の4役の定義を取り込む）と、プロット型の `character_requirements` を含める。
- `name`：入力は、S3 で割り当てた音6個と、名前の響きの説明文だけ。`element: name`。出力は `{"name": "...", "reading": "カタカナの読み"}`。検証：`reading` が、与えた音のうち2個以上を含む（`uses_given`）。
- `profile`：入力は、その人物の名前・役・割り当て要素（主人公は `taboo` を含む）。 事実シートとの整合は保つが、身長・出身地・家族などの全項目を本文へ列挙する必要はない。既存の手順が要求する名前・役・年齢・性別・種族・能力・願望・課題を字数内で統合し、不要な列挙で上限を超えない。事実・主語・字数の検証は変えない。
- 長い項目（profile・appearance・personality・values・backstory・relationship・voice・inner_conflict）は `output: text`、`extend_to_min: true` とし、本文だけを書かせる。短い項目（intro・motive・catchphrase）も `output: text`（`element: text`）とし、本文だけを書かせる。name は `element: name`。
- `motive`：入力は、その人物の名前・役・プロフィールと、他の人物の名前・役だけ。出力は本文だけ（120字以内）。主人公に「抑圧されている自己像」が割り当てられていれば、入力に含める。
- `intro`：短い紹介（50字以内で、文末記号で終わる1文。world-building の short_introduction）。`ends_complete` で検査する。
- `appearance`：外見と魅力（年齢・性別・種族・体格・装い。150字以内。heroes・heros-journey の外見の項目）。
- `catchphrase`：決め台詞（一人称で始まる1文。heroes の catchphrase）。

### S6 構造展開 [C]
- 入力：`assignment.json`、構造テンプレート、プロット型。
- 処理：
  1. （筋ごとの出来事数は S3 で決定済み）
  2. 各筋の出来事数を、その筋のテンプレートの段階に配分する。各段階に最低1件を割り当て、残りは段階の重みに比例して配分する（端数は seed で決める）。
  3. 副筋のスロットを、主筋の段階の間に seed で配置する。大河では、部を番号の順に並べ、部の間や部の中に他の部のスロットを差し込まない。これにより、全スロットの時系列の順序が決まる。
  4. プロット型の必須の出来事（§4.1）を、指定された段階のスロットに割り当てる。
  5. 各スロットに、登場させる人物を割り当てる。段階が要求する役の人物を必ず含め（同じ役の人物が複数いる場合は seed で選ぶ）、ほかに0〜2人を seed で加え（必ず含める人物が1人もいない場合は、ほかに1〜2人）る。要求する役が「不在の役」の場合、人物は割り当てず、段階の `absent_role_note`（例：「敵対者は、人物ではなく状況や内面の力として現れる」）をスロットに付ける。
  6. 段階に `object: true` が付いている場合、スロットに物語の `object` を付ける。
  7. 各スロットに、世界の抜粋に使うセクションを決める：段階の `world_sections` に挙げられたセクションのうち、この run で生成したものを最大2つ、挙げられた順に選ぶ。1つもない場合は「場の描写」を使う。
- 出力：`slots.json`。S7 のタスクをスロットの数だけ生成する。

### S7 出来事生成 [L]
- S7.event の `card.material_rule` は「入力にない人物・物・設定・事実を加えない。入力の素材から、手順が求める当段階の局所行動・変化を具体化してよい。」とする。条件の変更、根拠のない外部の出来事、前後段階・全体の計画を許可しない。既定の一律の追加禁止行は重ねない。
- タスクの単位：スロット1つの項目1つ（`S7.event-e<3桁>-<項目>`、`element: text`、各120字以内）。項目は `what`（何が起きたか）→ `where` → `when` → `why` → `intent` → `result` → `emotion` → `foreshadowing` の順に1つずつ実行し、同じスロットの先に決まった項目をカードに示す。`what` のタスクは `candidates: 3`、`select_candidate: least_similar`（Phase 1 は `candidates: 1`）。候補タスクは `S7.event-e<3桁>-what-c<n>`、選ぶコードタスクは `S7.select-e<3桁>` とし、後続の項目は選ばれた `what` をカードに示す。`least_similar` の比較対象（[task-model.md](task-model.md) §7）は、同じバッチの他の run のすべてのスロットの、選ばれた `what` とする。
- `who` は推論させない。S6 がスロットに割り当てた人物を、コードが `who` として記録する。
- `what` と `result` は、割り当て人物の既知の名前を冒頭の主語として書く。共同主語は割り当て人物の名前を「と」または「、」でつなぎ、最後に「は」または「が」を付ける。NFKC 正規化後に照合し、外側の引用符を許すが、名前自体の引用符は保存する。他の人物への言及だけでは不合格にしない。名前がすべて未定なら照合を行わない。`event_subject` の検証で誤主体を不合格とし、既存の修正・再試行・省略の経路で進む。
- 固定条件は不変の因果制約であり、今の段階ですべて発動・解決する命令ではない。生成する項目1つと現在の段階の働きだけを書く。場所は場所、時は時、理由は原因、意思は目標、感情は状態、伏線は後につながる手がかりを表し、他の項目の行動・結果全文で置き換えない。解決行動は段階の定義・指針が要求する場合に書く。 禁止条件が明示する行為を出来事で実施することは条件違反であり、S7.event と S7.detail の共通手順で、その行為を実施しないことを明示する。禁止を破った帰結が本文にないというだけで因果の反転とは判定しないが、禁止行為そのものへの違反は S8 の不合格対象である。
- 項目別の回答範囲の文面は `harness/story/tasks/S7.event.yaml` の `card.steps` を原本とし、`what：`、`where：` など項目キーと全角コロンを先頭に付けて各項目1文ずつ定義する。コードはキーの欠落・重複を検査し、「生成する項目」に対応する1文だけを選ぶ。共通手順は保持し、他項目の指示文をカードに含めない。 この選択・厳密検査は S7.event v13以降、または項目キー付き手順を1文以上持つ定義に適用する。それ以前で項目別手順を持たない定義の描画は従来どおりとし、v13の全キー欠落や部分欠落・重複・空本文・不明な指定項目はエラーにする。生成する項目に対応する回答範囲をカードに「作り方の指示」として示す。他の項目の回答範囲やパイプライン全体は示さない。`what` は現在の段階の働きを満たす行動、`where` は場所・位置、`when` は時点・時間的な関係、`why` はその行動の原因、`intent` は行動前に目指すこと、`result` は行動後に確定する変化、`emotion` は出来事を受けた感情状態、`foreshadowing` は入力の物・言葉・状態に基づく未解消の手がかりを書く。場所・時・原因・意思・感情・伏線を、完了した行動と結果全体の再述にしない。入力にない将来の出来事を断定しない。 各項目の専用手順には、指定項目だけを答える書式の短い独立した例を示せる。例中の物・人物は出力の素材ではなく、実際の本文には入力の素材だけを使うことを明記する。
- 先に決まった項目と直前の結果は、矛盾を避けるための前提であり、全文を再述する指示ではない。 素材に根拠のない人物・物・設定・外部の出来事を追加することと、入力の人物・物・状態を組み合わせ、現在の段階の働きを満たす局所的な行動・変化を具体化することを区別する。後者は生成する項目の処理として行う。固定条件の発動行動だけに限定せず、既存素材への観察・扱い・照合・選択などを現在の段階に沿って構成できる。入力にない素材や条件を創作し、前後の段階や物語全体を計画することは認めない。同じ物・言葉を反復する段階でも、完了した行動・結果の進展のない再演とは区別する。象徴的事物・葛藤・主題の反映は、生成する項目の回答範囲内に限る。既存の固定条件・人物・世界・段階・入力予算と検証は維持する。
- S7.event v18 の共通手順は、段階の定義・指針・必須の出来事・不在の役・象徴的事物・葛藤・主題を文脈として扱う。行動と変化を担う `what` / `result` では当段階の働きを満たし、他の項目ではその文脈と矛盾させず専用の回答範囲だけを書く。時点・場所・感情など各項目に必須の出来事全体や象徴・葛藤・主題のすべてを再述させない。入力・専用手順・条件・検証・候補・予算は維持する。共通手順の文面はタスク定義を原本とし、バージョン更新で旧キャッシュを分離する。
- S7.event v17 の `card.input_order` は `conditions` → `previous_result` → `object` → `characters` → `world_sections` → `conflict` → `climax` → `theme` → `glossary` → `event_field` → `decided_fields` → `stage_definition` → `stage_guidance` → `required_events` → `absent_role_note` とする。固定条件と完了済みの結果を先に置き、当段階の作り方の指示を手順の近くに置く。入力値・必須条件・直前の結果・切り詰めの優先順・検証・候補は変更しない。
- 入力：
  - スロットの段階の定義文。割り当てられていれば、プロット型の必須の出来事の説明、`absent_role_note`、`object`
  - そのスロットに割り当てた人物の ID・名前・役・動機
  - S6 で選んだ世界セクションの body（最大2件）
  - 同じ筋の直前の出来事の `result` だけ（それ以前の出来事は渡さない）
  - その筋のプロット型の `conflict`。段階がクライマックスに当たる場合（段階の `climax: true`）は `climax` も
  - 物語の「解決すべき主題」（割り当てられていれば）
- 出力：各項目の本文だけ。コードがスロットごとに `{"when", "where", "who", "why", "intent", "what", "result", "emotion", "foreshadowing", "sources"}` に組み立てる（後続の段階と `story.json` はこの形を使う）。
  - `intent`：人物の意思（world-building の protagonist_actions の「意思」）、`emotion`：出来事で人物が受ける感情（受動的な感情）、`foreshadowing`：後の出来事への伏線（実行者はすべてのスロットで書く。筋の最後のスロットの伏線は、S9 がコードで空にする。最後かどうかをカードに示さないため：P1）
- 検証：各項目120字以内（`max_chars`）。

### S8 整合確認 [C+L]
- [C] 各項目の字数。
- [L] 矛盾の確認。1回の確認は、2つの記述だけを入力とする別のタスク `S8.compare-<スロット>-k<n>`（kind: llm）とする。
  - 矛盾とは、2つの記述が事実として両立しないことだけを指す（同じ人物が同時に別の場所にいる、記述Aで確定した結果を記述Bが理由なく覆す、存在しないはずの人物・物が現れる、など）。人物の心情・関係・状況の変化や展開は矛盾に含めない。カードにこの定義を示す。
  - `S8.plan` は比較対象ごとに `comparison_kind` をコードで記録する。固定条件の対象は `conditions`、過去の出来事の対象は `events`。条件どうしの比較は S8.compare ではなく、「§9.5 筋の条件と本文の品質」の `S8.condition_check` で行う。`S8.compare` のカードはこれを必須入力として示し、Aの種類を先に区別する。固定条件には実施済みの行動・結果がなく、条件に従ったBを再演とは判定しない。条件の追加・反転・置換は従来どおり不合格とする。
  - 出来事どうしでも、入力にない同時性・同一場面・全人物の必須参加を補わない。人物・場所・時が異なるだけでは事実の矛盾にならず、実際に進展のない再演の検査は維持する。共同主体から一部主体への変更や主語・表現の変更だけで、進展のない再演を免除しない。入力に独立した別出来事が示されている場合は同様の行動・結果でも再演とせず、独立性を入力にない事情で補わない。`yes` の理由には、入力で実際に食い違う前提・行動・結果を具体的に示す。
  - 質問：「記述Bは、記述Aの結果と矛盾しますか」→ `element: judgement`、`{"answer": "yes|no", "reason": "1文"}`（出典はコードが記述A・BのIDを記録する）
  - スロットごとのコードタスク `S8.judge-<スロット>` が、そのスロットの compare の結果をまとめ、`yes` があれば S7 を無効化する。
  - 記述Aとして比較する出来事：(a) 同じ筋の直前の出来事、(b) スロット k の `who` の各人物が、時系列でそれより前に `who` として登場した直近の出来事（(a) と同じものは除く）。比較相手は `S8.plan` が S7 の出力から決める。S7 が無効化されて再生成された場合は、`S8.plan` も依存により再実行され、比較相手を決め直す。1スロットあたり最大3件とし、(b) が多い場合は時系列で近いものを優先する。
- いずれかが `yes` の場合、そのスロットの S7 を無効化する（[task-model.md](task-model.md) §4.3）。無効化するのは最初の項目 `what` のタスクで、他の項目のタスクは依存によって作り直される。候補生成をしている場合は、すべての候補タスクと、候補を選んだコードタスクをまとめて無効化する。S7 の `max_invalidations` は2とする。上限に達した後も矛盾ありと判定された場合は、S7 を失敗にせず、最後の出力を採用して manifest の `warnings` に記録する（無人で完走させるため。整合確認は品質の検査であり、物語の成立を止める条件ではない）。

### S7.detail 場面の詳述 [L]
- タスクの単位：出来事1件の場面（beat）1つ。出来事ごとの場面の数は §8 の配分で決める。場面の働き（発端・展開・転換・余韻など）は、コードが `tables/beats.yaml` から割り当てる。
- 依存：そのスロットの `S8.judge`（整合確認の後に詳述する）と、同じ出来事の直前の場面。
- 入力：出来事の記述（when・where・who・why・intent・what・result・emotion）、場面の働き、登場人物の名前・役・紹介・口調、S6 で選んだ世界の抜粋、同じ出来事の直前の場面の末尾（コードが600字を切り出す）。他の出来事の場面は渡さない。
- 出力：場面の説明的な記述（`output: text`、`extend_to_min: true`。三人称で、いつ・どこで・誰が・何をしたかが分かる書き方。小説の文体ではなく、正本としての説明的な記述）。字数は §8 の配分に従う。

### S9 正本組み立て [C]
- 入力：S3〜S8 の出力。
- 処理：
  1. 正本（§6）を組み立てる。`story.md` は、出来事ごとに、要約の1文（「いつ、どこで、誰が、何のために、何をして、どうなったか」の文型）と、その出来事の場面の詳述を時系列の順に並べる。`characters.md` は人物ごとの全項目、`world.md` は世界の全セクション・全項目を並べる。
  2. 文型に差し込む値は、末尾の句読点（「。」「、」）と、`why` の末尾の「ため」「から」「ために」を取り除いてから差し込む（「〜ためために」のような重複を防ぐ）。役は日本語の名前（`tables/roles.yaml` の `name`）で表示する。
  3. 分量（§8）を集計し、最低ラインに満たない資料があれば manifest の `warnings` に記録する。
  4. run がバッチに属する場合、重複除外とバッチの補充（§7）を行う。

## 4. プロット型と構造テンプレート

### 4.1 プロット型

- `tables/plot_types.yaml` に、heros-journey の21型を置く。各型は次を持つ。これらは開発者がテーブルとして記述し、実行時に LLM に生成させない。
  - `id`, `name`, `core`（中核の構造、1文）
  - `required_events`：必須の出来事の一覧（説明と、割り当てる段階）
  - `structure`：`standard`、または専用テンプレートのID
  - `character_requirements`（登場人物の要件）、`time_design`（時間の設計）、`conflict`（葛藤の種類）、`climax`（クライマックスの条件）、`pacing`（ペース配分）、`typical_setting`（典型的な舞台）：heros-journey と world-building のプロット型の項目を取り込む。各1〜2文
- `structure: standard` の型が14型、専用テンプレートを持つ型が7型ある。型の一覧は `tables/plot_types.yaml` を原本とする。専用テンプレートを持つ型の `required_events[].stages` には、標準の3テンプレートに加えて、専用テンプレートのIDをキーとする段階を置く。専用テンプレートを持つのは、段階構造に押し込むと個性が失われて中庸に収斂する型（タイムループ、断片的構成など）である（P4）。

### 4.2 構造テンプレートの選び方

- 構造テンプレートは `tables/structures.yaml` に置く。各テンプレートは段階の一覧を持ち、各段階は次を持つ：定義文、指針（heros-journey の段階ごとの指針と、骨子 A〜E の要素：予兆・挫折・代償など）、幕（`act`）、重み、要求する役、`absent_role_note`、`world_sections`、`object`（真偽値）、`climax`（真偽値）。
- 構造テンプレートは、任意で `chapters`（小説様式の章への割付）を持てる。各章は `id`・`name`・`stages`（段階 id の並び）を持ち、全章の `stages` を順に連結すると、段階の一覧と過不足なく一致しなければならない。`chapters` がない構造テンプレートは、1段階を1章とする（[format-pipeline.md](format-pipeline.md) §4.1）。
- 標準の構造テンプレートは3つある：`three-beat`（3段階）、`kishotenketsu`（4段階）、`heros-journey-12`（12段階）。段階の定義は `tables/structures.yaml` を原本とする。
- 主筋（および大河の各部の主筋）のテンプレートは、プロット型が `standard` の場合、その筋に配分された出来事数で決める。

| 筋の出来事数 | テンプレート |
|---|---|
| 5以下 | `three-beat` |
| 6〜11 | `kishotenketsu` |
| 12以上 | `heros-journey-12` |

- プロット型が専用テンプレートを持つ場合は、出来事数によらずそれを使う。専用テンプレートは、段階の繰り返し・省略の規則によって、任意の出来事数に対応する。繰り返し・省略は、各テンプレートが3段階以上と段階ごとの重みを持つことで表す（出来事数は重みに応じて段階へ配分する）。
- 副筋は常に `kishotenketsu` を使い、その副筋に割り当てたプロット型の必須の出来事を、`kishotenketsu` の段階に割り当てる（プロット型の各必須の出来事は、標準の3テンプレートそれぞれについて割り当てる段階を持つ）。

### 4.3 筋への出来事数の配分

- 副筋1本あたりの出来事数は、4〜6件を seed で決める。
- 主筋の出来事数 = 全体の出来事数 − 副筋の出来事数の合計。
- 大河では、部ごとに出来事数を決め（[scale.md](scale.md) §4）、各部を1本の主筋として扱う。大河の部に副筋は置かない。
- 主筋の出来事数が3未満にならないよう、出来事数の下限に副筋の分を含める（[scale.md](scale.md) §4）。

## 5. 名前の生成

LLM に名前を自由に作らせると、内部知識の典型的な名前に偏る（P4）。名前は、コードが与えた音から組み立てさせる。

- `tables/name_sounds.yaml` に、名前の響きの集合を置く。各集合は、響きの説明文（例：「硬い子音が多く、短い」）と、音（カタカナの音節）の一覧を持つ。特定の実在の言語・民族を指す名前は付けない。
- S3 が、各人物に響きの集合を1つ、その中から音を6個、seed で割り当てる。
- S5 `name` は、与えられた音のうち2個以上を使って名前を作る。

## 6. 正本

- `story.json`：形式は `schemas/story.schema.json` を原本とする（P1-11 で作成）。次を持つ：`meta`（run ID、seed、規模、入力由来の比率、筋ごとのプロット型、構造テンプレート、入力の種類、解決すべき主題）、`world`（世界セクションと一覧型の項目）、`cast`（人物：役、名前、読み、紹介、プロフィール、動機、外見、決め台詞、割り当て要素）、`threads`（筋：主・副、部、プロット型）、`events`（出来事：段階、筋、when・where・who・why・intent・what・result・emotion・foreshadowing、sources）。すべての要素に §2.1 のIDと `sources` を持たせる。
- `story.md`：`story.json` からテンプレートで生成する説明文。

## 7. 重複除外とバッチの補充

- 指紋：cast の名前・プロフィールと、events の全項目を、NFKC 正規化・空白除去・小文字化した上で連結し、sha256 をとる。指紋が同じバッチ内の既存の正本と一致すれば重複とする。
- 近似重複：events の `what` と `result` を連結した文字列の、文字3-gram の Jaccard 係数が、同じバッチ内の既存の正本のいずれかと閾値以上であれば近似重複とする。閾値は `tables/dedup.yaml` の `near_duplicate_threshold` を原本とする。
- 重複・近似重複の run は `duplicate` とし、バッチの要求件数に数えない。
- 補充：`st new --count N` は、最初に N 本の run を作る。S9 は `batch.lock` を取ってバッチの manifest を更新する。その run が `duplicate` になった場合に限り、作成数が上限 `max(3N, N+10)` に達していなければ、次の index の run を1本作る（heros-journey を継承）。これにより、`duplicate` 以外で終わる run の数は N を超えない。
- 比較の相手（「同じバッチ内の既存の正本」）は、バッチの manifest で `accepted` と判定済みの run の正本とする（`duplicate` の run と、S9 が未完了の run は含めない）。
- 判定済みの run の S9 が再実行された場合（後続の失敗からの `st retry` など）は、記録済みの判定を返し、補充をしない。
- 補充の run の index は、最初の N 本に予約した 0〜N-1 と既存の index のいずれよりも大きい最小の値とし、上限は index が `max(3N, N+10)` 未満であることで判定する。
- S9 は、`duplicate` と判定した run の状態を、manifest 更新（`status: duplicate`）で設定する。コードタスクが manifest 更新で設定できる状態は `duplicate` だけとする。

## 8. 分量の配分

[ADR-0007](../adr/0007-volume-floor.md) の最低ラインを満たすよう、コードが run の作成時（S0）とタスクの追加時（S3・S6）に、タスクの数と1タスクの字数を決める。

| 資料 | 最低ライン（規模倍率1の場合） | 満たし方 |
|---|---|---|
| 人物 | 合計10,000字 | 人物ごとの項目（S5）の字数の合計。主人公に多く、他の人物に少なく配分する（重みは `tables/volume.yaml`） |
| 世界 | 100,000字 | 生成するセクションの観点ごとの面（facet）の数と、一覧型の項目の数（S4） |
| 物語 | 100,000字 | 出来事ごとの場面（beat）の数（S7.detail） |

- 1タスクの字数の目安は、`tables/volume.yaml` に項目ごとに定める（例：場面 1,500〜2,500字、世界の面 800〜1,500字、人物の項目 300〜1,500字）。目安の下限を `min_chars`、上限を `max_chars` の検査に使い、カードにも目安を示す。
- タスクの数 = ceil(資料の目標字数 ÷ 1タスクの目安の中央値)。目標字数 = 最低ライン × 規模の倍率（`tables/scales.yaml` の `volume_multiplier`。掌編・短編 1、中編 2、長編 4、大河 8 を初期値とする）。
- 配分の結果は manifest の `scale.derived.volume` に記録する。
- S9 は実際の字数を集計し、最低ラインに満たない場合は警告を記録する（run は止めない）。

## 9. 事実の層と用語集

世界と人物の資料は、**事実の層**と**描写の層**の2層で作る。事実の層は、具体的・明示的で、誰が読んでも同じ世界を想起できる、客観性と再現性のある情報である。描写の層は、事実に従って書く情感のある記述である。事実の層を先に作り、描写の層の入力に渡す。

### 9.1 用語集（固有名詞の登録）
- 地名・組織名・用語・人名などの固有名詞は、すべて用語集に登録してから使う。用語集の項目は、ID、名前、読み、種類（地名・組織・用語・人物など）、1文の定義、登録したタスクを持つ。
- 用語集は専用のファイルに保存せず、`done` のタスクの出力から決定的に組み立てる。登録のしかた：
  - `element: name` のタスク（S5.name、S4.item_name、S4.calendar_name、S4.fact と S5.fact の名前の項目）の出力を、コードが登録する。種類と定義はコードが決める：S5.name は「人物」と「<役の日本語名>」、S4.item_name は項目が属するセクションの名前と「<セクションの名前>の項目」、S4.calendar_name は「暦」と「この世界の暦」、事実の名前の項目は §9.3・§9.4 による。
- ID は `g` に、`sha256("<登録したタスクのID>:0")` の16進の先頭6桁を続けたもの（例：`g3fa91c`）とする。後からタスクが追加されても、既存の ID は変わらない。衝突した場合は、組み立て時にエラーとして記録する。
- 固有名詞の名前は、コードが割り当てた名前の響きの音（§5）から組み立てさせる。
- 以降のタスクのカードには、そのタスクに関係する用語集の項目（入力に現れる ID の項目と、同じセクションの項目）だけを示す。
- `no_new_proper_nouns` は、「未登録の固有名詞を持ち込まない」検査として扱う。候補のうち、用語集とカードの入力に含まれるものは除外する。モードは、P1-14 で誤検出率を測り、基準を満たしたタスク種別だけを `fail` に切り替える（[phase-1.md](../plan/phase-1.md) の P1-14）。それまでは、すべてのタスクを `warn` とする。

### 9.2 世界の暦（S4.calendar）
- 現在の年（物語が始まる年）は、コードが run の seed で、`tables/world_facts.yaml` の `current_year_range`（初期値 300〜3000）から決める。LLM には推論させない。
- `S4.calendar_name`（`element: name`、run に1つ）：暦の名前。名前の響きの音（§5）を入力とし、コードが用語集に種類「暦」で登録する。
- `S4.calendar_epoch`（`element: text`、1文、run に1つ）：紀元（元年）の出来事。入力は暦の名前、現在の年、物語の `era`。
- すべての事実のタスクのカードに、暦の名前と現在の年を示す。事実の表や年表の「暦」の欄は、コードが暦の名前を書く。

### 9.3 世界の事実（S4.fact）
- 事実の項目は `tables/world_facts.yaml` に定める（原本）。各項目は、世界全体で一意のキー（例：`place.area`）、見出し（例：「面積」）、要素の形（`number`・`integer`・`year`・`name`・`text`）、単位（`number`・`integer` のとき）、値の範囲（任意）、属するセクションと観点を持つ。一覧型のセクションには、項目ごとに持たせる事実の項目（年・規模・構成員の数・所属など）を `item_facts` として、セクションごとに3〜8項目定める。
  - 例：地理（面積 km²、最高地点の標高 m、主要な地点の名前、地点の間の距離 km、季節ごとの平均気温 ℃ と降水量 mm、主な資源の名前と年間の産出量）、社会（制度・組織の名前、構成員の数、規則の条文の数、通貨の名前）、歴史（出来事の年、名前）、人々（人口、平均寿命、主な言語の名前）。
  - 曖昧な程度語では埋められない項目だけを置く。本文1つのセクション（`single`）では、1つの観点の項目は2〜6個とする（一覧型の `item_facts` は観点ごとではなく、セクションごとの3〜8項目とする）。
  - 同じ量は1つのキーで1回だけ定める。他の観点がその量を必要とする場合は、項目の `refers` にキーを挙げ、入力として参照する（再び推論しない）。
- タスクの単位：事実の項目1つ（`S4.fact-<キー>`、一覧型の項目は `S4.fact-<項目 ID>-<キー>`）。1回の推論で値1つを作る（[task-model.md](task-model.md) §2.5）。
  - `number`・`integer`：値だけを書かせる。単位はカードに示す。範囲外は再試行の理由とする。
  - `year`：`element: integer`。範囲は1以上、現在の年以下（未来のシナリオのセクションでは、現在の年より大きく、現在の年＋1000 以下）。
  - 一覧型の人々の加入年 `people.affiliation_year` は、同じ項目の年齢 `people.age` を `refers` で参照する。年齢が確定していれば、下限を `max(1, 現在の年 − 年齢)`、上限を現在の年とする。表に明示した範囲があれば、その範囲との共通部分を使う。年齢が未定・省略の場合は通常の `year` の範囲を使う。この範囲はカードの表示と submit の検査に同じ値を用い、範囲が1点・空の場合は task-model §2.5 の規則に従う。別項目の年齢は使わない。
  - `name`：`element: name`。名前の響きの音（§5）から組み立てさせ、コードが用語集に登録する（種類は項目の見出し、定義は「<セクションの名前>の<見出し>」）。
  - `text`：40字以内の1句（例：主な資源の種類）。
- 順序：同じセクションの事実の項目は、表の順に1つずつ実行する。一覧型のセクションでは、項目（S4.item_name の1件）ごとに `item_facts` を表の順に1つずつ実行し、項目どうしは並行に実行する（項目をまたいで直列にしない）。一覧型の項目のカードには、前提セクションの事実と、その項目の先に決まった事実を示す。各カードには、同じセクションの先に決まった事実、前提セクションの事実、`refers` の事実を、コードが「見出し：値 単位」の行で示す。セクションどうしは並行して実行できる。
- 測定の年（事実がいつの値か）は、現在の年とし、コードが表に書く。
- S4.section（描写の面）・S4.item の入力には、その観点・項目の事実と、関係する用語集の項目を含め、手順に「事実と矛盾させない。事実にない数値・固有名詞を加えない」を加える。

### 9.4 人物の事実（S5.fact）
- 事実の項目は `tables/character_facts.yaml` に定める（原本）。項目と要素の形：
  - 年齢（`integer`、範囲は割り当てた `age`・`species` の要素を入力に示して推論させ、0〜1000 の範囲で検査する）。生年はコードが「現在の年 − 年齢」で求める。
  - 身長 cm（`number`）、体格（`text`、40字以内）、職業（`text`、40字以内）
  - 出身地・居住地（`choice`：用語集の地名の項目から1つ。地名が1つもない場合は `name` として新しく作り、用語集に登録する）
  - 所属（`choice`：用語集の組織の項目と「なし」から1つ）
  - 家族：人数はコードが seed で0〜3人に決める。1人ごとに、続柄（`text`、10字以内）→ 名前（`name`）の順に作る。
  - 年表：件数は `tables/character_facts.yaml` の `timeline_count`（初期値 4）。1件ごとに、年（`integer`、範囲は生年以上・現在の年以下）→ 出来事（`text`、60字以内）の順に作る。表ではコードが年の順に並べる。
  - 技能：件数は3。1件ずつ（`text`、40字以内）。割り当てた `ability` の要素を入力に示し、それを具体化させる。
- タスクの単位：人物1人の事実の項目1つ（`S5.fact-c<n>-<キー>`）。人物の名前（S5.name）の後に、表の順に1つずつ実行し、先に決まった項目をカードに示す。人物どうしは並行して実行できる。
- S5.fact v3以降の技能は、既存の直列順を保ち、CODEがキー`skills.1`・`skills.2`・`skills.3`から担当範囲を選ぶ。対応する手順はタスク定義の`card.steps`にキー付きで保持し、1は能力の基本的な使い方、2は1と異なる対象や状況への応用、3は先の2件と異なる他者との共同作業への応用とする。能力の作用・制限を変更せず、実施済みの出来事としては書かない。他の技能の手順はカードに出さず、1推論1技能を保つ。
- 同版には今回の事実キーと、対象人物の先に確定した技能だけの配列を専用の必須入力として渡す。先行技能は省略されたものを含めず、入力予算のために切り捨てない。既存の`previous_facts`も維持し、旧版とS4.factは変更しない。技能1と技能以外の項目には空配列を渡す。技能以外の既存入力値・手順・検査は変えず、追加2入力と版によるキャッシュ分離は適用する。最初の技能に先行S5.factがなくても入力を解決できるよう、CODEがS3.assignの対象項目ビューへ現在キーと先行技能を補う。
- 同版の技能では、外側の空白とUnicode正規化NFKC後に先行技能と完全一致する回答をコードで不合格にする。言い換えの同義性まではコードで判定しない。エラーには重複した技能と今回の担当範囲を示し、既存の修正・試行上限・省略に従う。技能以外にはこの検査・担当手順を適用しない。版と実入力を通常のキャッシュキーへ反映する。
- 同版の技能の修正カードには、不合格理由の種類によらず今回の担当手順・事実キー・先行技能を保持する。字数や内部情報の不合格を直す際も生成時の担当範囲を失わせない。
- S5.fact の文章値（`text`）には、構造の説明と内部 ID を書かず、人物は入力の確定名で表す。既存の `no_story_metadata` で不合格とし、task-model §6.7 の修正・格上げ・省略で扱う。数値・名前・選択肢 ID などの機械値にはこの文章検査を適用しない。S5.fact の版を更新して以前のキャッシュと分離し、旧版定義と S4.fact の検査は変更しない。
- 人物の他の項目（profile など）の入力に、コードが組み立てた対象人物1人だけの事実のシートを含め、事実と矛盾させない。カード用のシートには、対象人物の確定した名前（`name`）も含める。関係人物の名前・役・紹介を渡す場合も、その人物の事実シートは渡さない。

### 9.5 出力
- S9 は、`world_facts.md`（世界の事実を、暦・表・年表で。年表は `year` の事実と一覧型の項目の年から、コードが年の順に並べる）、`glossary.md`（用語集）、`world.md`（描写）、`characters.md`（人物ごとに、事実のシートの後に描写）を出力する。
- 事実の層の字数は、世界・人物の分量（§8）に含める。

### 9.5 筋の条件と本文の品質
- S6 の後、筋ごとに `S7.condition` が発動条件・禁止・解決条件を1件ずつ順に確定する。入力は最初のスロットの局所的な世界・事物・葛藤と主人公の禁忌、先に確定した条件だけ。各条件は本文1つであり、失敗した条件は未定として進む。事物と禁忌は S3 の割り当てを参照する。条件は後続の S7.event・detail、S8 の比較と正本 events の `conditions` に渡し、追加・反転・別の条件への置換を認めない。
- S7.condition v2 以降の専用手順は、タスク定義の `card.steps` に `trigger：`・`prohibition：`・`resolution：` のキーつきで各1件置く。CODEは既存の `condition_kind` の指定に対応する1件だけを表示し、その他の共通手順は維持する。旧v1でキーがなければ旧手順を維持し、新版の欠落・重複・空本文・未知の指定はエラーにする。発動条件は行為・状態を前提とする作用の帰結、禁止は禁じる行為を明示し違反の帰結、解決条件は葛藤の解決が成立する前提と解決の帰結だけを書く。先に決まった条件と両立させ、その全文を別種類として再述しない。同じ行為を含むだけでは不合格とせず、条件の役割を区別する。短い独立した書式例は素材に持ち込まない。
- S7.condition の `card.material_rule` は「入力にない人物・物・設定・事実を加えない。入力の素材から、指定された条件の前提と帰結を具体化してよい。」とする。確定済みの条件の変更・反転・置換は許可しない。入力・1推論1条件・順序・候補・既存検証・予算は維持する。
- 条件どうしの検査（S7.condition v3 以降）：カードの指示だけでは、互いに両立しない条件の組が確定することがある。その組が残ると、どの出来事もいずれかの条件に反し、S8 が出来事の側を無効化し続けて解消しない。これを防ぐため、2件目以降の条件を、同じ筋で先に確定した条件と比べ、後の条件だけを直す。
  - 対象：条件の種類の順（`trigger` → `prohibition` → `resolution`、`plot_quality.CONDITION_KINDS` の順）で2件目以降の条件、つまり `prohibition` と `resolution`。条件IDは既存の `S7.condition-<スロット>-<kind>`（`<スロット>` は筋の最初のスロット）。
  - 追加するタスク：S6.expand v5 は、S7.condition の定義の `version` が3以上のとき、`prohibition`・`resolution` の条件ごとに次の2つを、条件と同時に（静的に）追加する。動的な追加・作り直しはしない。
    - LLMタスク `S8.condition_check-<スロット>-<kind>`（新しい種類 `S8.condition_check`、version 1、`element: judgement`、`output: json`、添字は `[<スロット>, <kind>]`）。依存は `S6.expand`、同じ `S7.condition-<スロット>-<kind>`、先の種類の各 `S7.condition`。
    - コードタスク `S8.condition_judge-<スロット>-<kind>`（新しい種類 `S8.condition_judge`、version 1、添字は `[<スロット>, <kind>]`）。依存は `S6.expand` と、同じ `S8.condition_check`。
  - 既存タスクの依存への追加：`prohibition`・`resolution` の S7.condition は、従来の依存（`S6.expand`・`S3.assign`・先の種類の条件）に加えて、直前の種類の `S8.condition_judge` に依存する（`prohibition` は依存先の judge がないので従来どおり、`resolution` は `S8.condition_judge-<スロット>-prohibition` に依存する）。その筋のすべての S7.event・S7.select・S7.assemble・S8.plan は、従来の条件への依存に加えて `S8.condition_judge-<スロット>-resolution` に依存する。S7.detail・S8.detail・S9.assemble には直接の依存を加えない（推移的に満たされる）。S6.expand 以外の既存の種類の `version` は変えない。
  - 入力（CODE が整形する）：`S8.condition_check` の入力スロットは `condition`（label「今回の条件（記述B）」、`from: S7.condition`、`select: condition`、required: true）と `decided_conditions`（label「先に確定した条件（記述A）」、`from: S7.condition`、`select: decided`、required: true）。CODE は依存の S7.condition から、`condition` に同じ添字の条件の本文を、`decided` に先の種類の条件のうち `done` のものを種類の順に「<種類の日本語名>：<本文>」の行で並べた文字列を渡す。日本語名は `plot_quality.CONDITION_LABELS`。`max_input_chars` は 2800、切り詰めない。
  - 検査しない場合：今回の条件が `skipped`、または先の種類の条件がすべて `skipped` の場合、`S8.condition_check` は claim されず、依存が満たされた時点で `skipped` になる（理由「比較する条件が未定」。task-model §4.2）。judge は skipped の check を「両立する」として扱う。
  - カードの文面（`S8.condition_check` のタスク定義の原本にこのとおり置く）
    - role：「筋の条件が、先に確定した条件と両立するかを検査する。」
    - steps：
      1. 「記述Bは今回の条件、記述Aは先に確定した条件。どれも出来事ではなく、物語が守る制約である。」
      2. 「記述Bと記述Aのいずれかを、両方とも満たす出来事が論理的に存在しえない場合だけ yes とする。例：Aが行為Xを必要とし、Bが同じ行為Xを禁じる。Aが状態Yの成立を帰結とし、Bが同じ状態Yの不成立を帰結とする。」
      3. 「扱う行為・物・状態が異なるだけ、一方の帰結が他方の前提になる、同じ行為に言及しているだけの場合は no とする。言及しない事柄を否定とみなさない。」
      4. 「reason は、両立しない行為・状態をB・Aから具体的に1文で示す。no の場合も根拠を1文で示す。入力外は補わない。」
    - output_example：`{"answer": "...", "reason": "..."}`
    - 検証：`schema: schemas/tasks/S8.compare.schema.json`（同じ形式を共用する）、`no_copy_from_inputs`、`avoid_listed`（`tables/meta_terms.yaml`）、`min_chars`（`field: reason`、`n: 1`）。`on_exhausted: skip`（skipped の check は judge で「両立する」として扱う）。
  - judge：`S8.condition_judge` は check の出力が `answer: yes` のとき、今回の条件 `S7.condition-<スロット>-<kind>` を無効化する。理由は「先の条件と両立しない：<reason>」とし、reason の中の「；」は「;」に置き換える。先に確定した条件は変更しない。無効化の上限は judge では判定せず、orchestrator が task-model §4.3 に従って処理する。出力は `{"slot": "<スロット>-<kind>", "invalidated": true|false}`。
  - 上限：S7.condition v3 は `max_invalidations: 2` と `on_exhausted: skip` をタスク定義に明記する（card・inputs・検証は v2 と同じ）。上限を超える無効化が要求された場合は、§4.3 の例外として、今回の条件を `done` から `skipped`（未定）にし、失敗報告と manifest の `warnings` を残す。その条件の check・judge の出力と、依存先の状態はそのまま残し、後続の条件と出来事はその条件を未定として進む。満たせない条件の組を出来事に課さない。
  - 出来事と条件の矛盾を S8 が検出したときに出来事を無効化する扱い（`comparison_kind: conditions`）は変えない。S8.compare・S8.judge の定義と版も変えない。
  - 適用範囲：S6.expand v5 が新しく作るグラフだけ。S7.condition の定義が v2 のとき、または既に作られたグラフには、検査タスクも依存も追加しない。新しい種類のキャッシュは既存の種類と共有しない。
- S8 は直前の出来事に加え、確定した条件との矛盾も1回の判定で検査する。出来事どうしでは、同じ行動と結果を言い直すだけで進展しないことも不合格とする。 条件の前提・帰結への非言及は否定とみなさず、それだけを矛盾にしない。「前提なら帰結」という因果制約から「帰結なら前提」や「その前提だけで帰結が起きる」を導かない。入力が明示する禁止・必要条件・前後関係の追加・反転・置換は引き続き矛盾として検査する。 禁止行為の実施と、未実施の能力・可能性・意思・条件の引用を区別する。 禁止は能力が存在しないという命題ではない。能力・可能性の記述から禁止の解除や許可も導かず、禁止と両立する。禁止の解除や許可を本文が明示した場合は、従来どおり条件の反転として検査する。「探せるようになった」「探したい」「探すと帰結がある」の記述だけから「探した」を導かない。本文が実行として記す禁止行為は、帰結が非言及でも従来どおり不合格とする。引用や可能性の記述に実施した行為が併記されていれば、その実施を検査する。判定手順の文面は S8.compare / S8.detail の定義を原本とし、旧キャッシュと分離して入力・検証・予算を維持する。
- S7.event の `what` は入力素材を当段階で誰がどう扱うかが読める局所行動を、`result` はその後で物・記録・関係・状態のどれがどう変わったかを具体的に書く。段階の定義・指針を達成したという宣言だけ（例：意味を反転させた、全体像を示すことに成功した）を行動・結果に代えない。正解内容や特定語の一律禁止は追加せず、既存の素材による局所具体化と1項目の範囲・主体・予算・検証を保つ。
- S7.event のwhat以外では、短い出力でも先に決まったwhat全文の完全コピーを `no_repeated_event_field` で不合格にし、対象項目の範囲へ修正する。段階の具体性をコードで意味判定する検査ではない。版を更新して旧キャッシュと分離し、旧版の検査は変えない。
- S7.detail は beat の担当部分だけを書き、他の beat の行動・結果を再演しない。本文の構造説明・内部 ID と、直前の場面の繰り返しはコード検証で不合格にし、修正の推論で直す。
- S9 は同じ筋・時・場所・人物で行動と結果が重複する出来事をコードで除外する。正本の分量不足は既存の警告で記録する。
- 各場面の `S8.detail` は出来事の行動・結果・確定条件と本文、直前の場面の末尾だけで矛盾と再演を判定する。条件と本文の前提・行動・帰結および前後関係を照合し、同じ前後関係を逆転と判定しない。条件を満たしたことだけでは再演にならず、直前の実施済み場面の再演を検査する。`S8.detail_judge` は不合格の beat だけを無効化し、上限では警告を残して進む。後続 beat はこの判定の完了を待つ。

## 10. 生成物の品質の検査

実機の生成で見つかった問題に対して、次の検査をコードで行う。

| 検査 | 内容 | 不合格のときの扱い |
|---|---|---|
| `no_copy_from_inputs` | 出力と、カードの入力の本文との最長共通部分文字列が、`tables/dedup.yaml` の `max_copy_chars`（初期値 60字）以上 | 不合格（理由に写した部分を示す） |
| `character_identity` | S5 の描写項目で、対象人物名に直接係る現在年齢・生年が事実シートと異なる | 不合格（正本の値を示す）。字数修正の対象にしない |
| 継続の重複の除去 | 継続で連結するとき、既出の段落と同一、または文字3-gram の Jaccard 係数が 0.8 以上の段落を取り除く | 取り除いて警告を記録 |
| `avoid_listed`（作り方の語） | 出力に、作り方の情報を表す語（`tables/meta_terms.yaml`：「名前の響き」「プロット型」「切り口」「タスク」「カード」「枠組みで進行」など）が含まれる | 不合格 |

- カードの「入力」節では、物語の素材（要素・事実・用語集・前の出来事など）と、作り方の指示（名前の響き・切り口の役割など）を、見出しで区別して示す。作り方の指示は、出力に書かないことを手順に明記する。
- S9 の要約文は、文の継ぎ合わせをやめ、「いつ／どこで／誰が／目的／行動／結果」を項目として並べる書式にする。
- 物語の分量の配分では、場面の数を、1場面の字数の目安の**下限**で割って求める（小さいモデルが目安より短く書く傾向を見込むため）。

### 10.1 人物の同定の機械的な検査

- `character_identity` は、カードの `facts.name` を対象名とし、NFKC 正規化後の符号付き十進整数（正負号は任意）を比較する。対象名の前が文頭・空白・句読点である明示記述だけを扱う。
- 現在年齢は「対象名はN歳」「対象名の年齢はN歳」「対象名は現在N歳」を、`facts.age` と比較する。
- 生年は「対象名は／が（暦名）N年に生まれた」「対象名の生年は（暦名）N年」「対象名は（暦名）N年生まれ」を、`facts.birth_year` と比較する。暦名を明示した場合は `facts.calendar` と一致する表記だけを扱う。
- 別人物の年齢・生年への言及、過去の年齢（「対象名はN歳のとき」「対象名はN歳だった」等）や否定した年齢・生年（「対象名はN歳ではない」「対象名はN年に生まれたわけではない」「対象名の生年はN年ではない」等）、年表の年、引用内の記述は照合しない。対象人物の名前を省略した文、任意の言い換え、意味的な人物取り違えはこの検査では判定できない。別人物の名前に言及しただけでは不合格にしない。事実シートが未定または比較する値がない場合、その値の照合は行わない。

- `profile`・`intro`・`appearance`・`personality`・`values`・`inner_conflict`・`backstory` は本文を対象名を主語にした「対象名は」または「対象名が」で始める。カードにこの規則を示し、`character_identity.require_subject: true` で検査する。先頭の空白と開き引用符は許容する。この規則で、別人物を冒頭の主語にする取り違えを拒否する。`voice`・`catchphrase` の一人称や `relationship`・`motive` の他人物から始まる記述には、この冒頭規則を適用しない。

- S7.detailでは同じ本文内の長い文の完全一致反復を `no_repeated_sentence`（[task-model.md](task-model.md)）で拒否し、通常の修正へ渡す。意味上の進展は既存S8判定の対象とし、検証で本文を削除しない。新しい版のみ適用し、旧v13のカード・検証・キャッシュは維持する。
