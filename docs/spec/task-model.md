# spec: タスクモデル

- 所有範囲：タスク定義の形式、タスクカードの形式、DAG とタスクの状態、claim/lease、検証、再試行、候補生成、長文の継続、キャッシュキー

## 1. タスクの種類

| 種類 | `kind` | 実行するもの | 例 |
|---|---|---|---|
| コードタスク | `code` | オーケストレータ（即時実行） | 組み合わせ（S3）、構造展開（S6）、組み立て（S9） |
| LLMタスク | `llm` | 実行者 | 素材抽出（S1）、出来事生成（S7） |

## 2. タスク定義

タスク定義は `harness/<pipeline>/tasks/<task_type>.yaml` に置く。1ファイル = 1つのタスク種別。形式は `schemas/task-definition.schema.json` で検証する。

```yaml
id: S5.profile               # タスク種別ID（<段階>.<名前>）
version: 1                   # 手順・スキーマ・入力の組み立て方を変えたら上げる。キャッシュキーに含まれる
kind: llm
output: json                 # json | text
max_input_chars: 3000        # タスクカードの入力部分の文字数予算
candidates: 1                # 候補数（§7）
max_attempts: 3              # 検証不合格時の試行上限（§6）
share_across_runs: false     # true なら run 間でキャッシュを共有する（§9）
lease_minutes: 30

inputs:                      # 入力スロット。値はオーケストレータが埋める
  character:
    from: S3.assignment
    select: "cast[{slot}]"   # その人物の役と、割り当て要素（IDつき）
    required: true
  name:
    from: S5.name
    select: "output[{slot}]" # 同じ人物の S5.name の出力
    required: true
    truncate: none           # 予算を超えたときの切り詰め方：none | tail | head | drop

card:
  role: 与えられた属性だけを使って、人物のプロフィールを書く。
  steps:
    - 入力の属性（願望・能力・役割）をすべて使う。
    - 入力にない固有名詞・地名・組織名を加えない。
    - 300字以内の日本語1段落で書く。
  output_example: '{"profile": "...", "sources": ["want:i07", "duty:t12"]}'

validate:
  schema: schemas/tasks/S5.profile.schema.json
  checks:
    - sources_exist
    - max_chars: {field: profile, n: 300}
    - no_new_proper_nouns: {fields: [profile], mode: warn}
```

- `card` には、そのタスクに必要なことだけを書く。パイプライン全体、他のタスク、物語の最終形への言及を書かない（P1）。
- 1タスクの出力は、1項目、または小さなJSONに限る（P5）。複数の項目が必要な場合は、タスクを分ける。
- 長いリスト（20件を超える要素）は、1回20件を上限に分割したタスクとして定義する。
- `select` で使える式は、`storyteller/selectors.py` に実装した名前つきの関数とフィールド参照に限る。任意のコードは評価しない。

## 3. タスクカード

タスクカードは、タスク定義に入力を埋め込んで生成する Markdown である。形式は固定とする。

```markdown
# タスク <ticket>

## あなたの役割
<card.role>

## 入力
<入力スロットを、IDつきで列挙する。例：[want:i07] 願望：誰にも見せない場所を持ちたい>

## 手順
1. <card.steps[0]>
2. ...

## 出力形式
次のJSONだけを出力すること。前後に説明を書かないこと。
<card.output_example>

## 守ること
- 入力に書かれていないことを付け加えない。
- 出力形式以外の文章を書かない。

## 前回の不合格理由        ← 再試行のときだけ
<理由>
```

- カードは自己完結させる。実行者がカード以外のファイルを読まなくても実行できなければならない。
- 入力部分が `max_input_chars` を超える場合、スロットの `truncate` に従って切り詰める。`required: true` のスロットを切り詰めても予算に収まらない場合は、タスク定義の誤りとしてエラーにする。
- カードには、run・パイプライン・段階を示す情報を含めない。カードの見出しには、タスクIDではなく、claim ごとに発行する不透明な `ticket`（ランダムな16進文字列）を書く。タスクIDは、段階・スロット・候補番号を含むため実行者に見せない。
- 入力素材のIDは、素材を区別するための記号として見せてよい。IDの体系は [story-pipeline.md](story-pipeline.md) §2.1 に従う。

## 4. DAG とタスクの状態

- run ごとに、タスクの依存関係を DAG として持つ。`st new` の時点で規模から決まる部分と、コードタスクの実行結果によって後から展開される部分（例：S6 がスロット数だけ S7 を生成する）がある。
- タスクの状態：

| 状態 | 意味 |
|---|---|
| `blocked` | 依存が未完了 |
| `ready` | 実行可能 |
| `claimed` | 実行者が claim 中（lease の期限つき） |
| `done` | 検証に合格し、出力を保存済み |
| `failed` | 試行の上限に達した |
| `skipped` | 不要になった（例：要素プールが必要量に達した後の S2 タスク） |

- **無効化**：後続の検査（S8、F4）が `done` のタスクの出力を不合格とした場合、コードはそのタスクを無効化する。無効化は、状態を `done` から `ready` に戻し、試行回数を1増やし（したがってタスクの seed とキャッシュキーが変わる）、次のカードの「前回の不合格理由」に検査の理由を書く。無効化されたタスクの出力に依存していたタスクは `blocked` に戻し、その出力を破棄する。依存していたタスクが `claimed` の場合は、その claim を取り消し（`claim.json` を `claim.revoked.<n>.json` に改名）、その ticket による提出を拒否する（終了コード 3）。
- 無効化の回数は、タスク定義の `max_invalidations`（既定2）で制限する。上限を超えた無効化が起きた場合は `failed` にする。無効化の回数は `max_attempts` とは別に数える。

- `failed` のタスクがある run は `stalled` になる。`st retry` で `ready` に戻すまで、その run は進まない。`st retry` は、試行回数と無効化の回数を0に戻す（過去の試行は `attempts/` に残し、manifest に retry の記録を加える）。

## 5. claim と lease

- `st next` は、`ready` のLLMタスクを1つ選んで claim する。対象は、`active` の run と、バッチの分析（[report.md](report.md)）のタスクである。選ぶ順は、作成順 → DAG の深さ順 → タスクID順とする。
- claim は、タスクディレクトリに `claim.json` を排他的に作成する（`os.open(path, O_CREAT | O_EXCL | O_WRONLY)`）ことで行う。作成に成功した実行者だけが、そのタスクを実行できる。
- `claim.json` には、実行者ID・隔離の種類・ticket・claim 時刻・lease の期限を書く。実行者は ticket で提出し（`st submit <ticket>`）、オーケストレータは ticket からタスクを引く。
- lease が切れた claim は無効とする。次に `st next` を実行した実行者が、期限切れの `claim.json` を `claim.expired.<n>.json` に改名してから claim し直す。無効になった claim による提出は拒否する（終了コード 3）。
- 並行実行を保証するのは、同じマシン上の同じファイルシステムに限る（[data-layout.md](data-layout.md) §5）。

## 6. 検証と再試行

`st submit` で提出された出力を、次の順に検証する。

1. **形式**：`output: json` の場合、JSON として解析できること。解析できない場合は、最初の `{` から、それに対応する `}` までを取り出して再度解析する。
2. **スキーマ**：`validate.schema` の JSON Schema（Draft 2020-12）に適合すること。検証には `jsonschema` を使う。
3. **チェック**：`validate.checks` に書いた検査。

| チェック | 内容 |
|---|---|
| `sources_exist` | `sources` の各IDが、そのタスクの入力に含まれている |
| `max_chars` / `min_chars` | 指定フィールドの文字数 |
| `count` | 配列の件数 |
| `ids_subset` | 指定フィールドのIDが、指定した入力スロットのIDに含まれる（例：S7 の `who`） |
| `uses_given` | 指定フィールドが、入力で与えた素材のうち n 個以上を含む（例：S5 の名前が与えた音を含む） |
| `no_new_proper_nouns` | 入力にない固有名詞の候補が現れていない（§6.2）。一般語の許可リストが存在しない場合は、入力だけを除外の対象とする |
| `ends_complete` | 本文が文末記号で終わっている |

- 不合格の場合、試行を `attempts/` に保存し、理由をつけてタスクを `ready` に戻す。次のタスクカードの「前回の不合格理由」に理由を書く。
- 試行回数が `max_attempts` に達したら `failed` にする。

### 6.1 JSON の出させ方（LLMアダプタ）

`config/models.yaml` の `json_mode` で、モデルごとに指定する。

| 値 | 動作 |
|---|---|
| `schema`（既定） | サーバーの構造化出力機能に、タスクの JSON Schema を渡す |
| `json` | サーバーの JSON モードだけを使う |
| `off` | サーバーの機能を使わず、プロンプトの指示と §6 の救済だけに頼る |

`schema` または `json` で空の応答・解析不能な応答が2回続いた場合、アダプタはそのモデルについて1段階下の値に切り替え、manifest に記録する（先行リポジトリで、一部のモデルが JSON モードで空応答を返した問題への対策）。

### 6.2 固有名詞の検出（`no_new_proper_nouns`）

形態素解析を使わない近似の検出である。

- 候補とする文字列：
  - 3文字以上のカタカナの連続
  - 「」『』で囲まれた文字列
  - 大文字で始まる英単語
  - 漢字の連続に、固有名詞を示しやすい接尾語（国・王国・帝国・町・村・市・島・山・川・教団・会・社・家・様・氏）が続くもの
- 候補のうち、次のいずれかに含まれるものは除外する：
  - そのタスクの入力の全文
  - 一般語の許可リスト `tables/common_words.yaml`
- 残った候補があれば、`mode` に従って扱う：
  - `warn`：合格とし、候補を manifest に記録する
  - `fail`：不合格とする
- Phase 1 では、すべてのタスクを `warn` で運用して誤検出率を測る。誤検出率が 5% 未満のタスクから `fail` に切り替える（P1-14）。

## 7. 候補生成

- `candidates: k`（k ≥ 2）のタスクは、同じカードで k 個のタスクを作る。タスクIDに候補番号を付け、カードの入力は同一にする。seed だけが異なる。
- k 件がそろったら、後続のコードタスクが1件を選ぶ。選び方はタスク定義の `select_candidate` で指定する。
  - `random`：タスクの seed による無作為選択
  - `least_similar`：比較対象との、文字3-gram の Jaccard 係数の最大値が最も小さいもの。比較対象は、同じバッチの他の run の同じタスク種別の出力とする。バッチに属さない run、またはバッチ内に比較対象がまだない場合は、`random` で選ぶ
- LLMに候補の優劣を判断させない（P4）。

## 8. 長文の継続

`output: text` で、タスク定義の `continuation: true`（`output: text` の既定値）のタスクは、出力が途中で切れた場合に継続タスクを作る。`continuation: false` のタスクは、途中で切れた出力を不合格とする。

- 途中で切れたと判断する条件：アダプタが長さによる打ち切りを報告した、または 400字以上で `ends_complete` を満たさない。
- 継続タスクのカードには、それまでの出力の末尾と、「既出の文章を繰り返さず、末尾の直後から続きを書いて完結させる」という指示を入れる。末尾の長さは、`max_input_chars` から他の入力の文字数を引いた残り（上限 6000字）とする。残りが 1000字未満になるタスク定義は、読み込み時にエラーにする。
- 継続は2回までとし、それでも完結しない場合は、元のタスクの試行1回分として不合格にする。
- 継続の出力は、元の出力と連結してから検証する。

## 9. キャッシュキーと再利用

- LLMタスクの出力は、次のハッシュをキーとしてキャッシュに保存する。
  `sha256(タスク種別ID, version, 正規化した入力, 候補番号, seed)`
- 同じキーのタスクが生成されたら、実行者に渡さず、キャッシュの出力で `done` にする（P6）。
- `share_across_runs: true` のタスクは、キーから seed を除く（試行回数は含める）。同じ入力から作る run の間で、出力が共有される。
- 入力の正規化：JSON のキーを整列し、文字列を NFKC 正規化する。
