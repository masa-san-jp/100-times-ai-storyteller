# spec: 生成物の評価手法

- 所有範囲：生成物（正本・様式化した出力・バッチの傾向分析）を評価する観点、手順、評価の原則

## 1. 目的と原則

ハーネスが設計原則（[VISION.md](../VISION.md) P1〜P8）どおりに、ユーザーの入力と要素テーブルから多様で追跡できる物語を作れているかを、ユーザーと開発者が確かめるための観点と手順を定める。

- **評価は診断ではない。** 評価の対象は生成物とハーネスであり、ユーザー本人ではない。生成物から、ユーザーの内面・性格・状態について断定や診断をしない。先行リポジトリの非断定・非診断原則（heros-journey の batch_analyzer。[lineage-inventory.md](../lineage-inventory.md) の「分析」の行）を継承し、[report.md](report.md) §1 と同じく、正本の実例に基づく観察と、問いの形での提示にとどめる。
- **点数で優劣をつけない。** 総合点・順位・合否の判定を作らない。観点ごとに、根拠つきの観察を記録する。
- **評価のための新しい機構を作らない。** 評価は、既存の成果物（正本、`manifest.json`、タスクの入出力、`report.json`）を読む手順として定める。評価のためだけにタスク・テーブル・コマンドを加えない。
- **コードで確かめられることは、コードの検証に任せる（P2）。** 本 spec の観点のうち、機械的に確定する項目は §3 に示す既存の検証の結果を確認するだけとし、評価者の判断に置き換えない。
- **LLM に評価させない（P1）。** LLM に生成物の全体を読ませて「良し悪し」を判定させる手順を定めない。判断が必要な観点は、ユーザーまたは開発者が行う。
- **評価の記録は生成物ではない。** 評価の記録はユーザーのローカルディレクトリにだけ置き、リポジトリに含めない（P8）。評価のために、生成物や入力をネットワークへ送らない。

## 2. 評価者と対象

| 評価者 | 目的 | 主な対象 |
|---|---|---|
| ユーザー | 自分の入力から、意図しない中庸さや偏りなく物語が作られたかを振り返る | 正本、様式化した出力、傾向分析（[report.md](report.md)） |
| 開発者 | ハーネスの原則が守られているかを確かめ、仕様・テーブル・タスク定義の改善点を見つける | 上記に加え、`manifest.json`、タスクの入出力、検証の結果 |

評価の単位は、物語1本（run 1つ）と、バッチ（同じ入力から作った複数の run）の2つとする。

## 3. 評価の観点

観点は、原則ごとに分ける。種別は、[C]＝既存の検証の結果を確認する、[H]＝人間が正本や出力を読んで判断する、を表す。

| # | 観点 | 種別 | 見るもの | 対応する原則 |
|---|---|---|---|---|
| E1 | 完走と再現性：run が `completed` か。`skipped` のタスクの理由が、`failure.md` と manifest の `warnings` に記録されているか（[task-model.md](task-model.md) §6.3）。同じ入力・seed で同じ割り当てになるか | [C] | run の状態、`manifest.json`、`tasks/<task_id>/failure.md`、割り当て（`assignment.json`） | P2, P6 |
| E2 | 出典の追跡：LLM タスクの出力に、カードに渡した素材の ID が `sources` として記録されているか | [C] | 各タスクの `output.json`（[story-pipeline.md](story-pipeline.md) §2.1）、正本の `sources` | P3 |
| E3 | 素材の出所：物語の素材が、ユーザーの入力・要素テーブル・前段タスクの出力のいずれかに辿れるか。辿れない固有名や設定が混入していないか | [H] | 正本と `sources` | P3 |
| E4 | 正本の形式と分量：run が `completed` であること（S9 で `schemas/story.schema.json` の検証を済ませている）。`manifest.json` の `warnings` に、最低ラインに満たない字数の警告（[story-pipeline.md](story-pipeline.md) §8）が記録されていないか。参照整合の確認先は spec に定めていないため、この観点では扱わない | [C] | run の状態、`manifest.json` の `warnings` | P2 |
| E5 | 様式の忠実さ：様式化した出力が、正本の出来事・人物・世界を欠落や改変なく含むか。様式の検証（F4）を通っているか | [C]+[H] | 様式化した出力、様式の検証の結果（[format-pipeline.md](format-pipeline.md)） | P1, P2 |
| E6 | 中庸への収斂の少なさ：バッチの run どうしで、プロット型・割り当てた要素・役・モチーフが偏らず、近似重複が除外されているか | [C]+[H] | `report.json` の集計（R1）とモチーフ群（R3） | P4 |
| E7 | 入力とのつながり：入力の傾向が、物語の中で何らかの形（主題・葛藤・雰囲気など）として現れているか、あるいは現れていないか | [H] | 正本と入力の抽出結果。ユーザーが読む | P3, P8 |
| E8 | 個人情報の不在：入力が取り込み時の検出（[input.md](input.md) §4、`st new` / `st check-input`）を通っていること [C]。正本・出力に個人を特定できる情報が含まれていないか、評価者が目視で確かめる [H] | [C]+[H] | 取り込みの結果、正本と出力 | P8 |
| E9 | 小さい実行者での完走：再試行の回数、`failed` や `skipped` になったタスクの偏りが、特定のタスク種別に集中していないか | [C]+[H] | `st status` の `tries`・`failure_report` | P5 |

- E3・E7 は、LLM に判定させず、ユーザーが読んで判断する。
- 観点の追加と変更は、本 spec を変更して行う。

## 4. 手順

1. **対象を決める。** 評価する run またはバッチを決める。run が `completed` でなければ、E1 の観察として記録し、E2 以降は完了した範囲だけを見る。
2. **機械的な観点（[C]）を確認する。** E1・E2・E4・E8（取り込み時の検出の確認）、および E5・E6・E9 の [C] 部分について、既存の検証の結果と成果物を読み、結果を記録する。失敗があれば、どの成果物のどのタスクかを書く。
3. **読む観点（[H]）を確認する。** E3・E5・E6・E7・E8・E9 の [H] 部分は、評価者が正本・出力・傾向分析を読み、§5 の形式で観察を記録する。バッチを評価する場合は、複数の run を並べて読み、違いと共通点を書く。
4. **所見をまとめる。** 観察を、次のいずれかに分けて記録する。
   - 入力の振り返り（ユーザー向け）：入力のどの傾向が、どの run のどの記述に現れたか。現れなかったか。問いの形で書く。
   - ハーネスの改善点（開発者向け）：どの原則・観点が満たされなかったか。仕様・テーブル・タスク定義のどこを見直すかを、Issue として起票する（[README.md](../README.md) §4 の規則に従い、原本を更新する）。
5. **評価を使って、生成物を書き換えない。** 評価の所見は、次の run の入力やテーブルの増補の材料にしてよい。ただし、既存の run の正本・出力を、評価のために書き換えない（P6）。

## 5. 記録の形式

評価の記録は、観点ごとに次を書く。形式は Markdown とし、置く場所はユーザーが決める（データディレクトリの外でもよい）。

| 項目 | 内容 |
|---|---|
| 観点 | E1〜E9 の番号 |
| 対象 | run ID またはバッチ ID |
| 観察 | 正本・出力の実例に基づく事実。実例には、run ID とタスク ID または出来事 ID を付ける |
| 問い | 入力との関係を問う疑問文（任意。E7 では必須） |

### 5.1 書いてはならないこと

- ユーザー本人についての断定・診断・性格や心理状態の推定（例：「この人は〜という傾向がある」「〜の問題を抱えている」）。
- 点数・順位・合否・優劣の判定。
- 実例を伴わない印象だけの評価。
- 入力の原文の引用（P8。入力の傾向は、抽出された短い語句で示す）。

## 6. この spec が決めないこと

- 評価を自動化するコマンドやタスク。必要になった場合は、先に本 spec を変更し、[cli.md](cli.md) などの該当 spec に追記してから実装する。
- 傾向分析（`st report`）の処理。原本は [report.md](report.md) とする。
