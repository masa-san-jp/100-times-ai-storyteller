# 実装の進め方

- 所有範囲：実装に関わる役割、作業の受け渡し、報告の形式、レビューの基準、作業場所の規則

## 1. 役割

| 役割 | 担当 | 行うこと | 行わないこと |
|---|---|---|---|
| 所有者 | リポジトリ所有者 | 原則層（VISION・ADR）の決定 | — |
| オーケストレータ・レビュアー | Claude Code | 作業項目の割り振り、仕様層の変更、レビュー、push・プルリクエスト・マージ | 作業項目の実装 |
| 実装者 | Codex（gpt-5.6-luna、推論 xhigh） | 1つの作業項目の実装・テスト・ローカルでのコミット | 仕様の変更、push、範囲外の変更 |

- 仕様層の変更権限は、オーケストレータに集約する。実装の都合で仕様が書き換わることを防ぐためである（[docs/README.md](../README.md) §3）。
- 実装者が仕様の不足・矛盾・曖昧さを見つけた場合は、§1.1 の裁量の範囲を除き、自分で解釈を決めて実装しない。作業を止めて、§3 の「仕様への質問」として報告する。オーケストレータが仕様を更新してから、作業を再開する。

### 1.1 実装者の裁量

次に当てはまるものは、仕様に書かれていなくても実装者が決めてよい。決めた内容は、報告の「実装上の判断」に書く。

- 外部との取り決めに影響しないもの：内部のモジュール構成・関数名・クラス設計、コードタスクの処理名、アルゴリズムの選択、ロックの再試行の実装、テストの構成と故障の注入方法、人間向けの表示の体裁。
- 外部との取り決めとは、次のものをいう。これらは仕様で決め、実装者は決めない：データディレクトリに書くファイルの形式と場所、CLI の引数・標準出力の機械向けの形式・終了コード、タスク定義とテーブルの書き方、タスクカードの文面、状態遷移、seed とキャッシュキーの計算。

## 2. 作業の単位と流れ

1回の依頼 = 作業項目1件（`docs/plan/phase-N.md` の `P<N>-<番号>`）= ブランチ1本 = 作業場所1つとする。

- 依存関係が満たされた作業項目は、最大3件まで並行して依頼してよい。ただし、同じファイルを変更する見込みの作業項目は同時に依頼しない（組み合わせはオーケストレータが決める）。
- 実装者の推論レベルは `high` を既定とする。次の場合は `xhigh` にする：仕様の検査、状態遷移・claim・無効化など誤りが後に響く作業項目（Phase 0 では P0-08・P0-09・P0-11）、`high` で2回続けてレビューに通らなかった作業項目。

1. オーケストレータが、main を最新にし、§5 の作業場所にブランチ `impl/<作業項目ID>`（例：`impl/P0-01`）を作って、実装者に作業項目IDを渡す。
2. 実装者は、[AGENTS.md](../../AGENTS.md) の手順で文書を読み、作業項目の根拠の spec に従って実装し、テストを書き、ローカルでコミットする。
3. 実装者は、§3 の形式で報告する。
4. オーケストレータは §4 の基準でレビューする。修正が必要なら、指摘を実装者に渡して 2 に戻る。
5. 合格したら、オーケストレータが push し、プルリクエストを作り、CI の成功を確認してマージする。作業項目の状態を計画書に反映する。

## 3. 実装者の報告の形式

```markdown
## 作業項目
P0-01

## 結果
完了 | 仕様への質問があり停止 | 失敗

## 受け入れ条件
| 条件 | 結果 | 確認したテスト |
|---|---|---|

## 変更したファイル
- path：変更の概要

## 実装上の判断
- 決めたこと：理由（§1.1 の範囲であること）

## 仕様への質問
- 文書と節：質問（どの解釈があり得て、どれを選べないのか）

## 実行したコマンドと結果
- uv run pytest：…
```

## 4. レビューの基準

1. 根拠の spec と実装が一致している。spec にない振る舞いを加えていない。
2. 受け入れ条件と、計画書の「共通の受け入れ条件」が、テストで確認されている。
3. 設計原則 P1〜P8 に反していない（特に、LLMタスクのカードに全体像を含めない、選択をコードで行う）。
4. [ADR-0002](../adr/0002-python-uv.md) の複数 OS の実装規則に従っている。
5. 作業項目の範囲外の変更がない。
6. オーケストレータ自身が `uv run pytest` と `uv run python tools/check_docs.py`（P0-03 以降）を実行して通る。

## 5. 作業場所の規則

- 所有者のリポジトリ（ファイル同期サービスの配下にある場合を含む）は、main を pull するだけにし、実装の作業場所にしない。
- 実装の作業場所は、作業項目ごとの git worktree とし、`~/.cache/storyteller-worktrees/<作業項目ID>/` に作る。マージした時点で `git worktree remove` で削除し、ブランチも削除する。これにより、作業場所が残り続けたり、ファイル同期の対象になったりしない。
- 仮想環境 `.venv` は各 worktree の中に作る（`.gitignore` で除外）。
- テストで作るデータディレクトリは、OS の一時ディレクトリ（pytest の `tmp_path`）に置く。リポジトリ内やファイル同期サービスの配下に作らない（排他制御のテストが同期の影響を受けないようにするため）。
